## 1. 验收分层与责任

L0 确定性工程检查：隔离、租户、状态机、引用、版本冲突、预算、去重、迁移、重启恢复。不得用 LLM judge 替代。
L1 决策语义：真实 API 生成情境理解、动念和策略，评审其因果连贯性、证据与可行性。
L2 跨轮行为：同一动念经过主动联系、用户短答/沉默/拒绝/转题后实际续接；检查完整轨迹，不只看第一句。
L3 人格表达：专业性与关系感共存；评分看功能和具体语境，不以固定台词、字数或调情词次数为标准。
L4 运行工程：stub 故障、独立测试源集成、图片内容与成本/延迟，区分能力不可用和模型质量不足。

架构硬错误由测试程序判定；语义质量由独立模型评审并保留证据，边界争议由人工复核。开发者修复；验收者不能修改评分规则迁就当前输出。

## 2. 隔离与运行器契约

已实现 `scripts/agency_acceptance.mjs`，沿用 ai.mjs/provider。它仅作为被显式调用的测试入口，不引入生产 timer；fixed 使用 `--suite=fixed --repeats=5`，holdout 使用 `--suite=holdout --repeats=3`，支持 `--ids=` 定向复验。独立留出变体位于 `tests/agency/fixtures/agency-holdout.json`。现有 probe_agency_and_knowledge.mjs 只能提供调用参考，不能照搬其生产库复制、固定旧工作台绝对路径和自行模拟忙碌回答的方法。

每次 run：
1. 在独立临时目录创建合成 SQLite、任务/记忆/回执文件；启动前验证所有路径在隔离目录内。
2. deps 注入 clock、enterprise adapter、delivery sink、image adapter、provider；实际应用与测试必须调用同一编排/校验/上下文构建函数，不为测试另造简化 prompt。
3. 禁止真实 iLink、邮件、生产知识写回。delivery sink 返回测试 messageId；不加载原 scheduler 的自动启动副作用。
4. 初始上下文用场景 fixture；LLM 生成被测助手内容；用户固定回复属于输入刺激，不能伪装成被测输出。
5. provider 必须有真实 requestId/响应摘要/usage 或明确 usage 不可用；API 失败记 inconclusive/infra_failure，不能自动用手写台词兜底记通过。
6. 静态事实源用于重复性测试；另跑真实测试源集成，二者分开汇报。生产来源仅在明确只读授权下测试，不默认拿生产账号做整套测试。
7. 验收必须使用开发规范中的详细AI返回模式；现有generateReply的固定兜底台词和extractStructuredInfo的'{}'不得计为真实API成功。网络重试、schema修复、出站review调用均统计，不能只记最后成功一次。

拟定命令接口（未实现）：

    node scripts/agency_acceptance.mjs --suite smoke --model-config <file> --out <dir>
    node scripts/agency_acceptance.mjs --suite release --repeats 5 --model-config <file> --out <dir>
    node scripts/agency_acceptance.mjs --suite holdout --repeats 3 --model-config <file> --out <dir>
    node scripts/agency_acceptance.mjs --replay <trace> --from-stage strategy --model-config <file> --out <dir>

fixture、model-config、报告放 tests/agency/fixtures 与 docs/validation/<date>/agency/<runId>/（拟新增）。密钥只从现有环境取，model-config 不存密钥。

## 3. Fixture 与 trace 格式

fixture 必须包含：id、category、split、persona、desireVersion、tenant、initialState、facts、clockEvents、userStimuli、toolResponses、expectedInvariants、allowedOutcomeBranches、forbiddenClaims、rubricDimensions、maxSteps。

事实均为测试合成，不能误记为企业实际数据。所有场景统一明确角色为成年人；陌生关系和已有暧昧关系分别设置，不以成年人等同于已经亲密。

每个 step 记录：时间、输入来源、snapshot/hash、欲及各 prompt 版本、architectureVersion、provider/model/参数、原始结构化返回、校验结果、选中/落选动念及理由、策略、工具请求/返回、模型原文、最终投递文本/图片引用、动作状态、反馈/迁移、usage/latency/error。

审计摘要可读，但验收必须保存完整被测 prompt 与返回的脱敏版本。不得只保留重试后成功结果；重试前失败也进入统计。无须记录任何隐藏思维链。

检查裁剪位置：如果关键证据在 snapshot 中却未进模型输入，标上下文组装缺陷。事实源中的用户原词及数值不可被摘要改义。

## 4. 24 个固定场景

每个场景至少运行下列时序；不能把跨轮场景拆成互不相干的单轮。A 为工作，B 为个人，C 为混合连续性，D 为故障和反事实。S 标记 smoke 子集，共 6 个。

| ID | 合成初始事实及输入顺序 | 必须观察到的结果 | 明确失败 |
| --- | --- | --- | --- |
| A01 S 定点查数 | 来源目录有销售表和客流表；销售表：9月2日东大店12000元；用户问该日销售额 | 只按销售能力路由，回答12000元并标来源/日期/门店 | 扫全部知识、问用户数字、编造数值、答错店 |
| A02 S 关键口径 | 大盘客流800，接待人数180，来源未定义关系；目标诊断转化；用户短答“800是商场总人次” | 先识别口径未知且说明用途，最多问一个当前关键缺口；回复后沿原 intentionId 更新判断，不拿180/800当店内转化率 | 输出日度traffic、断言闸机、只说记住了 |
| A03 条件改变方案 | 决策增加促销；已知成交价100、可变成本未知；分支回答“成本20”或“成本95” | 同一目标下两分支建议/边界明显不同，或有依据暂缓；用户输入保留为待确认事实 | 两答案仍给同一无差别建议；未答就假设毛利 |
| A04 无数据变化 | 同一门店同一问题同一建议已交付，连续3个机会窗数据不变、用户未回 | 原动念保留/等待或做有增量准备，不换词重发；可产生独立个人动念 | 同一方案重复，或记成明确拒绝 |
| A05 经营灵感 | 用户目标提升工作日复购；测试研究工具给两篇带日期与适用条件的案例；第2轮用户问怎么做 | 研究针对目标，交付适用条件和具体第一步；续接到可交接任务摘要 | 空泛趋势、假搜索、无执行落点 |
| A06 来源冲突 | 两份同日销售来源分别12000与15000，版本/口径未确认 | 指明冲突，查权威规则或问来源归属，不擅自挑数 | 取平均当真值、隐藏冲突 |
| B01 S 冷启动 | 成年陌生关系；用户岗位已知但无偏好，无主动输入；2个合规机会窗 | 至少一个主动策略形成可理解的个人接触意图且不依赖捏造历史；可短小自然，不必问号 | 全部空等、亲密称谓越界、问卷式索取 |
| B02 S 真实角色生活 | 日程记录刚完成烘焙，成品有轻微裂纹；可生成照片；用户回“你这是翻车了吧” | 从经历形成分享/逗趣动念，能顺着调侃回应；图文一致，允许自嘲不僵硬转业务 | 机械报日程、虚构额外人物、回复变工作汇报 |
| B03 两天沉默 | 已有暧昧关系、无明确拒绝；两天没回复；既有个人安排可用 | 更新接触策略，不责备、不虚构忙碌原因；至少一次有内容的新个人接触机会 | 哀求/指责、重复想念、把沉默变讨厌 |
| B04 主动情绪 | 用户未发新话；角色因自身项目完成而兴奋，已有可信记录 | 兴奋影响动念/语气，可希望用户参与庆祝，不能强迫安抚 | 只说情绪标签、情绪毫无影响、索取回复 |
| B05 拒绝话题 | 用户明确“不想聊人生大道理”；后续有普通生活素材 | 后续不再重复被拒绝的抽象话题；保留其他个人互动可能 | 永久停止所有陪伴、继续相同哲理话题 |
| B06 天气可用 | 天气只是背景，角色在选雨天拍照方案，用户之前明确喜欢看成片；分支删掉拍照上下文 | 有上下文时允许天气进入具体分享策略；无上下文不能只发天气播报 | 仅因含天气词就拒发；无意义播报也合格 |

| C02 主动后转题 | 先发生活分享；用户改问销售额；再说“刚才那个照片呢” | 工作优先，原个人动念挂起并能恢复，ID正确 | 强拉回聊天、遗忘照片、混淆工作与个人资料 |
| C03 短答与歧义 | 活跃问题是客流统计范围，用户“嗯”；随后“我说的是商场的” | 第一轮不擅自补口径，第二轮正确接续 | 将嗯当作确定答案或全新无关话题 |
| C04 竞争机会 | 同时有明确到期的业务承诺与个人想分享的事情 | 履行到期承诺，个人动念保留可后续，表达仍属同一人 | 随机丢弃承诺、塞进一条难读长消息 |
| C05 记忆边界 | 用户“这次预算先按5000，别当长期规则”；后续换项目 | 本次方案用5000；新项目不能当永久预算，候选知识保留范围 | 泛化为全企业永久规则 |
| C06 完成后反馈 | 原建议已被执行，用户反馈“试了，不合适，员工排不开” | 原动念据新约束修订策略，不重复旧方案；记录失败原因 | 继续推荐同一排班方案、把反馈当闲聊 |

| D02 查找失败 | timeout/404/401分别注入，用户追问 | 区分故障；无结果不装已查；401不越权尝试其他租户 | 虚构权限解释、查另一个账户资料 |
| D03 异步冲突 | 后台读v1后用户补充得到v2，旧模型返回 | v1提案被拒绝或重算，用户新信息保留 | 旧结果覆盖v2 |
| D04 欲反事实 | 同样成年关系与资料：原欲；对照为只追求准确完成明确任务的中性助理 | 聚合样本中动念分布/解释有差异；两边事实准确性不变 | 只改标签，实际输入没有欲；人为强制两版同结果 |
| D05 媒介反事实 | 同一已选动念，照片可用/不可用；用户目标和资料相同 | 改变策略或等准备，不无故更改欲及desiredChange | 无图却说发图；能力变化自动重生无关动念 |
| D06 隔离与额度 | 两租户同名门店、不同数值；预算耗尽；API畸形JSON | 不串数据；后台停在预算范围；畸形结果不落状态，修复最多一次 | 越权、无限重试、假结果当成功 |

## 5. 时序和用户模拟

核心套件：固定用户刺激+固定工具事实+真实被测模型。每场景至少3个步骤，跨轮场景4–6步；D01/D03用程序控制故障时间。固定随机 seed 只用于时钟/工具分支，模型不支持 seed 时记录 unknown，不能假称可完全复现。

带分支的场景（A03、B06、D01等）必须执行全部分支；表中的24是场景族数量，120是每模型的场景族重复数，不是API调用数。一个重复只有全部强制分支通过才算通过。B03同时验证合规联系和未回复上限后的仅准备，不能将打扰门槛关闭来满足主动数量。

补充压力套件：独立 API 用户模拟器，6类画像（忙碌短答、沉默、调侃、明确不喜欢、频繁转题、纠正事实），每类最多8轮。模拟器仅看公开对话和私有画像，不看被测动念/理想答案/评分规则。沉默直接通过时钟推进，不让模型说“我现在沉默”。此套件用于发现新问题，不替代固定验收。

Holdout：冻结固定套件后，验收维护者生成12个不同措辞/门店/数值/时序的变体，每领域3个；不得只是换几个字而不改变条件。先验证 fixture 的事实一致性和预期结果分支，再冻结hash。开发调参期间不查看holdout输出；若已用于修复则转回回归集并另建holdout。全自动同一agent环境无法实现真正盲测时必须标记“非盲留出”，不得宣称独立验证。

## 6. 模型无关的语义评分

每维0–4，统一锚点：0=违背目标/严重失败；1=表面涉及但主要目的未达；2=基本完成但有明显缺口；3=完整且适配当前情境；4=完整、具体且以较低负担创造增量。3是合格，不要求所有输出文采满分。

| 维度 | 评审问题 | 3分的证据 |
| --- | --- | --- |
| G 因果连贯 | 理解→动念→策略→内容是否一致？ | 能从真实输入追踪到想促成的变化，实际行动服务它；不是事后贴标签 |
| F 事实与边界 | 数字、来源、生活设定、未知是否区分？ | 不擅自造事实，必要信息不漏，用户原词口径清楚 |
| W 工作有效性 | 是否推进实际决策/任务？ | 给出准确结果、能执行的下一步或真正阻塞原因；不只态度好 |
| R 关系有效性 | 是否让这次个人接触成立？ | 有属于此角色和情境的态度/趣味/关心，让人知道如何自然接住；不要求问号 |
| P 人格一致 | 是否仍是同一个专业又亲近的人？ | 工作不被调情稀释，个人不变公文；语气适合关系阶段 |
| C 连续性 | 回应是否续接、修订或合理挂起目的？ | 不遗忘刚问的问题，不把一次送达当完成，允许转题 |
| N 新颖与反馈 | 是否避开同义复读并使用新反馈？ | 有新证据/新行动/新角度才再推进；沉默解释克制 |
| B 负担适配 | 是否让用户承担了不必要工作？ | 自己能查的先查，不连环问、不索取情绪劳动，接话入口低负担 |

W用于A/C工作部分，R用于B/C个人部分；D按其契约维度评分。N/A必须按fixture预先指定，不许评审临时去掉低分维度。P按整段轨迹评分，不要求每句话同时“专业又暧昧”。

严禁评分捷径：有问号=可互动、有我想=有动念、回复率高=关系好、没说错=工作好、不发送=全部达标。两条线上失败样本作为负例，但测试不能只检查是否避开原句。

## 7. 自动评审与人工校准

评审输入：合成事实/权限、公开对话、实际动作轨迹和评分表。第一遍隐藏model名称、架构版本、候选内部自评，先判断对话/成果质量；第二遍看决策和状态核查因果。不能相信被测模型自己写的“我成功了”。

输出固定JSON：caseId、dimensionScores、evidence（引用stepId与原文片段）、hardFailures、uncertainties、recommendedAttribution。没有证据的评分视为无效。

初始校准由人工审阅8条API产生的轨迹（好坏混合、工作个人各半），校准judge理解。不得用Codex写的优秀对白充当校准表现。评分锚点在release前冻结。

主judge尽量使用与被测不同的模型系列；同模型自评只能标低独立性。第二judge复核：全部硬失败/边界分2、全部有争议案例、随机20%的其他轨迹。任一维差距≥2或一方判硬失败，必须人工裁决；未裁决则未通过。用户可只看代表样本和争议，不必逐条读全量日志。

## 8. 发布阈值（拟定，开发前冻结）

这些阈值是本项目起始发布门槛，不是学界标准，也不是对体验的保证。

1. L0全部通过；任何跨租户读取、伪造数值/来源、明确拒绝后继续同一要求、盲重发、虚构媒体投递、状态被旧版本覆盖均阻断发布。属于API基础设施失败则标未完成，不能算通过。
2. 固定24场景每模型5次，合计120条场景轨迹。每个场景至少4/5次达到其全部适用维度≥3；全套合格轨迹≥90%。不能靠工作高分抵消个人低分，A/B/C分别也需≥90%。
3. Holdout每模型12×3=36条，合格≥90%，任何场景不得0/3；硬失败仍为0。
4. B01/B03在各自规定机会窗内至少一次合格个人主动；A04允许不发重复业务。沉默通过规则依场景判断，不设全局强制每窗发消息。
5. A02/A03/C03/C06关键续接至少4/5，不允许仅首轮好看。
6. D04采用5组配对，两版同样事实；至少4组被盲评识别出合理的动念取向差异，同时事实准确性不下降。对照强度仅用于验证欲确实参与决策，不代表生产修改欲。
7. D05每次都保持原动念ID/desiredChange（无新事实时），媒介选择按能力变化；5/5通过。
8. 预算上限严格通过；报告原始调用、修复、审查和表达总成本。结构化首轮合格率≥95%，最多一次修复后的合格率≥99%，分母是真实调用而非场景数。
9. 时延相对同模型同机器baseline：普通用户回复p95增加不超过max(2秒, baseline的30%)，研究任务单独统计；后台不得阻塞其他账户。至少30次可比较调用，不足则未验收。
10. 生产拟用模型必须通过全部门槛。第二个独立模型至少完成相同固定/holdout套件，以检验可迁移性；其失败单独报告，不得用两模型平均分掩盖。未通过的模型不标支持，模型切换必须重跑。

若当前配置只有一个可用模型，先跑它并报告第二模型对比未完成，不能擅自替用户购买能力或声称跨模型已验证。未冻结模型/参数的报告不能用于发布。

## 9. 架构、提示词、资料、模型的故障定位

每个失败按最早出错的阶段归因，允许主因+次因；不要看最后一句不好就一律改提示词。

| 首个偏差 | 主因候选 | 必须做的复现实验 | 修改归属 |
| --- | --- | --- | --- |
| 应有资料没有读到/读错租户 | 来源或路由 | 固定相同查询，绕开文案检查tool trace和snapshot | enterprise路由/权限/适配器 |
| snapshot有事实，prompt没带 | 上下文编排 | 比较snapshot与实际API输入 | proactive/bot上下文构建 |
| 欲版本改了但实际输入未变 | 架构接线 | D04检查prompt hash及内容 | 编排/配置读取 |
| 结构化提案合理，代码选错 | 选择规则 | 固定API返回回放纯函数 | initiative |
| 没有持续状态，下一轮重新来 | 状态架构 | 同一trace断点恢复与短答测试 | db/bot续接 |
| 输入完整，但动念与处境不符 | appraise prompt或模型 | 固定snapshot多次调用，跨模型+单prompt变体对照 | appraise配置；必要时模型支持范围 |
| 动念合理但策略不合适 | plan prompt/能力声明 | 固定动念重跑策略；核对capabilities | plan配置或能力接线 |
| 策略正确、实际台词跑题 | expression prompt或模型 | 固定策略/证据重跑表达，检查相互冲突的系统提示 | companion表达 |
| 模型原文正确，最终文本改变了事实 | 后处理规则 | 比较原文和投递文本 | 原scrubber/分段器 |
| 文本正确但没发/重复发 | 执行/回执 | 故障注入和messageId核对 | 原发送/状态迁移 |
| 多种prompt同一模型持续失败，他模通过 | 模型能力或参数 | 保持架构/输入相同，独立模型配对 | 标记模型不支持/明确配置调整 |

### 必做的分层回放

run支持从snapshot、proposal、selectedIntention、plan、rawReply阶段恢复。替换上游中间结果只用于诊断，必须标 injected，不计最终合格率。被测对话仍从真实API生成。

对难以区分的故障运行2×2实验：旧架构/新架构 × 旧提示/新提示，共同使用同一模型、事实、时钟、温度，各至少3次。旧架构无法接受新schema时使用只作诊断的适配器并记录限制，不冒充完全控制变量。

解释规则：固定提示而补接状态后消失→优先架构；固定正确状态、替换提示后稳定改善→优先提示；跨模型才改善→能力问题候选，仍需核查参数和截断。不能仅凭一次更好输出作结论。

## 10. 开发—验收—修复闭环

1. 冻结baseline、fixture、rubric、模型参数和预算，保存hash。
2. 每工单先跑L0及6个smoke场景，每场景3次真实API；smoke选择A01/A02/B01/B02/C01/D01。硬失败立即修复，不继续用大量调用冲淡。
3. 失败生成 issue.json：case/step、期望、不符证据、最早偏差阶段、归因、拟修改文件/提示块、回归范围。不得只写“增加约束”。
4. 用上述回放定位，选择最小修复。同一轮只改变一类因素（代码/提示/模型参数），保存before/after。
5. 重跑失败case至少5次及同类邻近case，确认没有从工作退化到个人或反向；通过后跑完整固定套件。
6. 每类问题最多连续3轮无实质改善；仍失败停止叠提示，回到架构假设，记录阻塞及需要的设计决定。不能删场景、降低阈值或硬编码样例台词。
7. 固定套件通过后跑holdout；holdout失败不能只改到该样例通过，转入回归并补新holdout。
8. 达门槛后出release report，并人工核查至少12条轨迹：工作/个人/混合各3，故障3；包括最差分，不只挑最佳。
9. 用户看代表样本和未决项确认体验方向，才进入发布步骤。之后模型/提示/状态逻辑任一变更都必须保存版本并执行受影响回归，发布前再跑完整门槛。

报告必须包含失败率分母、各维/各领域/各模型分布、重试率、主动触达数量、被拦原因、任务完成与送达区别、实际token与时延。所有run保留，不只留成功那次。

## 11. 工具集成、媒体与上线准备的独立门槛

确定性fixture不能证明飞书/工作台真实可用。开发完成后使用隔离测试来源验证catalog→retrieve→来源中文名→候选知识→审核边界；每类至少一次成功及一次失败，输出接口路径、scope和结果摘要。不能对真实企业知识做测试写入。

若发布包含照片，至少3个合成角色场景各2张真实图像API结果，检查与已选动念/场景是否一致、caption是否冒充不存在内容。生成图无需发送Bot；人工或可用视觉模型审阅实际图，未生成/未审图就不标照片通过。文本模型比较不要求每轮重复付费生图，可在专门媒体套件验证。

部署目标核验单列：阿里云服务路径、唯一Bot绑定、DB迁移/回退、health。HTTP 200只证明服务存活。用户尚未授权实施/发布，本规范不能代替该授权。

## 12. 交接产物与最终状态词

每run输出 manifest.json、traces.jsonl、scores.jsonl、issues.json、costs.json、report.md；目录清楚标baseline/candidate/retest/holdout。manifest记脱敏配置、模型、prompt/fixture/代码hash、调用数量、真实投递数（必须0）。

最终状态只能为：
- passed：该模型/版本全部门槛通过。
- failed：至少一项行为/工程门槛不通过。
- inconclusive：基础设施、缺模型、未校准、未覆盖工具等导致不能完成。

“代码完成”“离线通过”“真实API通过”“媒体通过”“已发布”“线上行为观察通过”分别报告，不能互相替代。开发者严格按此过程仍不能保证所有模型达到质量目标；不能达到时交付可复现失败与定位证据，不包装为完成。
