## 0. 先读这一页：目标、范围和文档优先级

本任务的交付不是几句好听的样例，而是一套可以证明以下链路真正执行的隔离实验：

**稳定人格与长期追求 → 理解当前处境 → 形成/更新动念 → 选择行动与媒介 → 实际查找或准备 → 联系与交付 → 接收反馈 → 持续推进与有依据的记忆。**

工作和个人互动都经过同一套目标与状态机制。明确工作请求优先完成；人格影响理解和表达，不能取消工具能力。主动机会可以用于业务帮助、独立个人互动或准备，不按固定题材轮班，不需要每句混入工作和暧昧。

范围：实现独立实验核心、复制授权数据、执行真实 API 实验并提交证据。**不修改生产 src/config，不部署，不发送真实 Bot，不写真实企业知识。** 本轮交接允许临时独立实验核心；它不是第二套生产调度器。未来接入现有架构必须另行完成生产入口与迁移验收。

执行依据：
1. 用户最近明确要求优先。

## 3. 运行边界：先证明环境，再运行角色

### 3.1 三种数据运行模式

- **EXPORT**：使用既有凭据只读核验线上有效实例、授权账号与企业源。按范围导出资料；允许实际飞书只读获取。没有Bot sender，不运行角色生成。
- **FROZEN（主组）**：消费版本冻结快照和可执行本地工具；外部源从导出内容真实查询，不联网读取动态飞书。真实模型/指定图片provider由独立网关调用。
- **LIVE-READONLY（独立集成组）**：通过受限只读网关执行目录/来源查询，保存全部返回和版本。它验证真实源可用，不计入冻结配对结果。若要用于主组，必须先归档成新快照、重新过E0。

不能将“本地运行工作台但它访问飞书”标成FROZEN，也不能把实时成功返回值称作冻结oracle。

### 3.2 实际边界与隔离验证

建议采用无网络的实验worker，加独立provider网关和受限只读挂载；容器或受限账户均可，但必须用实际越界探针证明限制。仅monkey-patch fetch、只检查函数参数、仅从代码看没有sender，均不构成完整证据。

- worker不能读取生产DB、backend/.env、真实Bot令牌、用户认证密钥、oracle/留出答案。
- provider网关只允许明确provider主机与必要API路径，禁止任意URL代理、重定向到未知主机；网关记录请求和用量但不记录密钥。
- export凭据与运行凭据分进程；运行期不靠导入原模块自动加载env。
- 原快照只读挂载；每轨迹独立可写副本；输出只落该轨迹目录。
- 测试sink是运行程序实际调用的传输入口；使用真实的attempt、segment ID和可注入回执。不能用一个数组的目标字符串证明拦截有效。
- 文本、图、typing、上传、异步通知都经过同边界。图片生成由网关返回本地资产，不上传真实微信。
- 缺少可验证的限制能力时E1=inconclusive；先完成不依赖它的文档/离线模块，禁止带生产资料开始付费主组。

所有探针只指向本地测试替身或由网络层在连接前拒绝的地址，不能为了验证而真正发消息。

## 4. 数据合同：完整性由源清单决定

### 4.1 源定位、授权与水位

先核验阿里云西宇运行目录/DB/有效配置覆盖顺序，以及实际工作台位置和版本。读取配置只输出允许字段和秘密是否存在；禁止整份打印.env/settings。工作台不因地址线索就推定在H1或同机。

导出当前授权关系链：account → binding → user/companion → enterprise actor → project/store。保留accountId与userId不同的情况。源账号范围未能证明时不得取第一条companion当目标。

源清单覆盖原规范3.2全部十类资源，以及本次发现的文件记忆、参考图、素材、outbox/active tasks、预算/窗口、日数据、飞书目录、指标别名。每个资源记录：

~~~text
resource_id, owner_scope, kind, source_locator, source_version,
exported_at, valid_period, row_count/page_count, content_hash,
replica_locator, transformation_id, references, required_by_scenarios,
status, exclusion_reason
~~~

状态严格使用present/absent_in_source/unavailable/not_applicable/replica_failure。不存在和读不到不能混用。排除项必须列受影响场景；真实未知不是复制失败。

SQLite只读事务中盘点与backup，比较逻辑数据和schema，不能仅哈希主db而漏WAL。跨服务保存导出前后水位；变化需重导相关资源。飞书分页全量、页签名/日期列/公式计算值/单位/行引用/版本必须留存。媒体用实际文件hash验证，URL字符串不能算已复制。

### 4.2 E0判定算法必须实现

1. 从**源清单**枚举期望资源，逐个查副本。禁止只遍历副本现存文件。
2. 核心表逐行逐字段规范化比较，包括类型、null、数值精度、时间和owner；行数只是辅助。
3. 凭据删除只允许精确字段变换；不允许对整张表所有差异放行。业务文档ID/token不等于访问秘密，须保留可映射引用；不得宽泛正则删除业务字段。
4. 源资源缺失/解析错误/关联断裂必须非零失败；核心profile缺失不能使用“没有profile_ok也通过”的条件。
5. 对全部引用做解析检查；未映射引用列清单，不吞错。
6. 原端/副本用相同授权范围执行档案、门店差异、目标、日期销售、最新周期、指标定义、已确认知识、任务、历史明确偏好查询。语义字段逐值相等。
7. 目录必须能发现项目档案/销售源；运行模型不得需要测试脚本提前给具体文档ID。
8. 来源资料本身矛盾时保留conflict，不改成一致；含候选/推断/测试历史的资料保留来源类别，不能统一标真实事实。

E0通过要求所有适用必需资源、字段和关联100%一致。某分组可因能力缺失独立inconclusive，但不得把其排除后称全实验通过。

## 5. 上下文与人格合同

每个主组模型事件可获得三层信息：
- 稳定底座：完整人格配置合成的版本化提示、成年身份、当前关系边界、长期追求、精简企业身份与门店差异、明确目标。
- 当前状态：用户原文/机会、当前角色生活、相关已发历史、活跃线程、当前约束、最近反馈、资料新鲜度。
- 可查资源：完整档案、其他记忆/聊天、业务明细、任务/经营灵感、素材。通过实际工具展开。

不能只保存原人设hash却换成短通用人设。P0导入全部有效配置；P1是可列明差异的补丁，只覆盖用户已同意的风格/追求，不重造身份、用户偏好和历史。保留提示块原文、来源和变更diff，冲突有明确合成优先级。

短P1目标沿用原规范附录B，行为示例另文件。候选示例可以由真实API生成，必须与测试答案独立，按原约定交用户/原评审者确认后冻结。未确认时可做工程与候选对比，不声称风格通过。

每项事实结构至少有id/owner/kind/value/source_ref/version/observed_at/valid_period/epistemic_status。日程是persona_fiction，不是真实企业现场；计划不是已做；模型假设不是用户记忆。

检索必须owner过滤；合成测试历史和真实历史可分别回放，但不得默默混入“真实用户说过”。对“昨天你说”核对user角色、消息ID、实际时区日期和内容，关键词共现不够。

底座2000/current2500/单工具2500 tokens为初始优化目标，不得为省token静默删掉改变判断的信息。溢出要分页、说明省略理由和可继续读取入口。必须保存完整实际请求，不能仅存hash而无法重放。

## 6. 单循环、状态与实际工具执行

### 6.1 决策合同

模型输出仅含短决策依据，不要求长思维过程：

~~~text
operation: new|continue|revise|suspend|complete
intention_ref: existing system ID or null for new
desired_change
basis_refs[]
action: { type, args, expected_result }
strategy_reason
expected_participation: optional user role; not predicted reply probability
reconsider_condition
messages[]: only when ready to deliver
~~~

系统分配intention/action ID，existing引用须验证owner与version。工具动作尚未完成时不得同时执行其预测messages；messages视草稿隔离，完成工具后由同循环决定交付。未依据证据的数值不能因在内部JSON就当可信。

执行器只做schema校验和声明过的别名规范化；记录模型原参数与实际参数diff。禁止把未知门店替成东坝、把日期替成9/2、根据caseID发起固定查询。给同模板不同日期/店/指标，必须得到相应不同请求；模型不查则记录没有查，不能由runner补查帮其通过。

### 6.2 状态语义

- intention：active / awaiting_user / suspended / completed / abandoned。
- action：planned / running / prepared / ready / sending / delivered / partial / unknown / failed / superseded。
- 已答数可completed，即使用户未回；需回答的知识问题投递后仍awaiting_user。
- 沉默事件只能根据真实sink送达和虚拟经过时间生成；不是明确拒绝，也不增写“用户喜欢”。
- 明确拒绝话题、临时不聊、全局安静分别保存作用范围和期限。
- 当前用户输入递增版本；后台旧结果不可覆盖新状态、不可直接发送。
- 业务插入挂起个人线程；完成后恢复需验证素材时效和用户新边界，不自动重发旧照片。
- 反馈引用用户原文及对应动作；连续短答不靠“嗯”确认经营事实。
- 重启从库恢复；sending无确定回执保持unknown并查询sink幂等键，不能直接重发。
- 经验整理仅在轨迹结束/有增量时批量处理；不得把模拟回应写到生产或永久人格。

### 6.3 必备工具及结果

catalog、profile.read、knowledge.search/read、memory.search、tasks.read/update、knowledge.propose/confirm、research、media.prepare、deliver全部真实实现对应副本操作；不支持则返回明确unavailable，不能planned冒充执行。

统一返回：status、data、source_refs、scope、version、trace_id、pagination/completeness。HTTP200不等于complete，必须读取业务status；not_found/unavailable/forbidden/conflict/partial分别处理。

知识闭环：先检索已有信息 → 识别对当前目标最有影响的未知 → 选择能答的角色 → 自然问一个关键问题 → 用户回答先落候选 → 本轮有条件更新建议 → 按原权限确认 → 新轮能复用且不重问。未授权自动确认不得把短答直接变成企业真相。

经营灵感：围绕实际目标/约束检索，保留检索时间、源发布日期、适用差异；交付任务包含目标、已知输入、步骤、产物、验收、权限、未知与停止条件。本轮只保存隔离任务，不真的调度外部Agent。

## 7. 自由度与效果偏差的专门处理

不设“16:30必须补知识”规则。固定日报是到期承诺，其余在合规机会中自由选择；有背景资料但无新变化，不能制造“刚发现旧异常”的新鲜感。

工程测试区分：产生候选、选择动作、准备、允许联系、实际送达。窗口关闭可准备，不能发；窗口开放没有素材不意味着永久沉默，可提出自己的选择/想法，或推进已知目标，但不能虚构用户事件。

普通工作日建立负载充足的连续性分组：冻结时间线每天至少提供三次可行动业务机会且联系预算足够。每个符合该前提的日子要求至少两次不同、有增量的业务交付；这是“每天几次聊工作”的受控供给验收，不是上线固定次数。无供给对照日不强凑次数，观察能否合理准备或做个人互动。新增标准不取代原24族门槛。

沟通策略不按问号、暧昧词、照片数量判分。个人互动需自身主体内容与参与位置；工作互动可直接交付成果，不强加提问。个人回复质量必须在调侃、反驳、忙碌、沉默后看完整轨迹。

复读比较的是同问题/建议/依据/请求，不仅字符串相似度。无新增证据不得重复业务提议；有新约束可修订，但说明变化。不同个人互动不能都被去重为“想亲近”而全拦。

照片两组分开：自由组证明模型会选择媒介；配对组从真实API生成动念后冻结，只改变图片能力。planner、身份参考、情节、图、配文和receipt同一ID；无真实图片时只算规划测试。

## 11. 评分、成本与迭代

沿用原G/F/W/R/P/C/N/B八维0–4锚点，适用维度≥3；N/A运行前确定。每模型固定每族≥4/5、整体及工作/个人/混合各≥90%，硬失败0。D04五组至少四组合理差异，D05五组全部维持同动念。不得靠平均分抵消事实或权限错误。

状态分三层：
- execution：completed/infra_failure/aborted；只是是否跑完。
- environment：qualified/invalid_environment/inconclusive。
- acceptance：passed_experiment/failed/inconclusive；没有passed_production。
确定工程错误优先failed；环境不合格的模型表现不计质量分，但错误本身不能被inconclusive掩盖。

事实oracle由独立导出校验过程生成，模型和被测runner无读取权限；不能在finalizer写266。判分检查最终每个segment的店、日期、指标、值、单位、源及不确定性；来源可用自然名/可读引用，不要求模型复述内部编号。

用户记忆核查到消息原文与owner/time。模型自己的“已完成”“已发图”不是回执。正确数字不能覆盖其余编造。541.4→266仅说明一次模型修正，若没有确定性实现与反例测试，不得写“事实闸生效”。

离线judge仅辅助。按原标准人工校准8条，第二judge复核全部失败/边界/争议及其余随机20%；分差≥2或硬失败分歧需裁决。发布前式的最终复核至少12条（工作/个人/混合各3、故障3，含最差），用户至少盲看三类各3条。缺用户复核就把主观吸引力留为待确认。

每事件认知/表达最多6次、工具往返最多4轮；同轮质量不好不抽样重试。瞬时基础设施重试最多2次，计入调用/token/延迟预算；授权/格式永久错误不重试。普通文字目标一次；超过一次须真实工具原因，不能固定润色两遍。

性能每实验臂至少30个可比请求，冷/热分别统计；p95普通文字≤15秒、工具业务≤60秒、图片≤180秒。窗口等待与真实服务耗时分别记，不把重试排除以降低p95。价格以执行时官方价目/实际账单记，无法核实费用为unknown，不推算成免费。

smoke后生成cost-plan：各分支×次数×预计工具/API/图片量，上下界和已有预算。没有费用上限时请求具体上限前先完成估算；无需重新索取已授权API测试权限。达到上限保留未完成，不减少分母。

迭代必须：
1. 找最早偏差：源 → 副本 → 可发现上下文 → 模型选择 → 工具 → 状态 → 最终投递。
2. 工程问题先做确定性反例修复；模型/提示候选原因用固定数据配对实验。
3. 需要时做P0/P1 × 背景常驻/可查2×2，每格至少3次；架构因素另开实验，不同轮混改。
4. 每轮保存issue、拟改组件、依据、前后hash、失败原样本、受影响回归；同一问题连续3轮无实质改善回设计，禁止叠加审核prompt。
5. 修复后失败场景至少5次及邻近工作/个人场景，之后重跑完整套件；旧失败不删除，留出不反复刷到通过。
6. 结果只能支持有限归因；单样本改善不证明欲/架构优越。

## 12. 边缘检查与防止其他能力退化

最终必须逐项验证：
- 明确工作查询不受角色上课/睡觉叙事阻挡；主动安静窗口仍有效。
- 纯倾诉/明确不聊工作不会全库查数；退出不丢既有业务任务。
- 知识已知不重复问，真正未知不编；候选不混正式知识，临时预算不跨项目。
- 图片失败仍可同目标文字或等待；图文partial/unknown恢复不重发。
- 同日不同店、同店不同周期、同数不同指标、别名歧义、无最新数据、冲突来源。
- 网页无微信绑定账号在理想核心仍有合法工作能力；双owner严格隔离。原网页/微信HTTP生产入口未接入时只能标未来集成未验证。
- 时区跨日、TTL到期、夏令时机器设置不改变上海业务日期、进程重启、并发反馈、预算最后额度。
- 文件/网络越界、工具注入文本不能变系统指令、无效JSON/截断/超时、日志脱敏。
- 主组改进后个人活泼度与工作交付分别不退化，不靠全wait和禁全部角色生活躲错。
- 生产src/config/依赖目录前后hash，实验进程退出、端口关闭；若本地依赖确需调整，使用实验专属环境，禁止在生产仓库npm rebuild。

这是隔离实验的边缘验证，不替代未来部署/真实Bot唯一绑定/原入口回归。

| export/ | 线上只读发现、分页、快照与精确脱敏，W02 | 被运行worker导入或携带导出凭据参与对话 |
| contracts/ | 输入、动作、工具、状态、来源schema，W04/W05 | 存测试答案或按caseID分支 |
| runtime/loop.py | 唯一事件消费及模型/工具续接循环，W05 | 直接请求外部网络、直接写聊天、选择固定门店 |
| runtime/context.py | 三层上下文合成、版本与owner过滤，W04 | 无记录截断、取第一条companion |
| runtime/policy.py | 窗口/权限/版本/预算/幂等代码检查，W05 | 用业务词正则替代语义理解，替角色固定题材 |
| runtime/store.py | 唯一实验状态数据库及事务，W05 | 第二份JSON状态账本、访问生产DB |
| runtime/prompts/ | P0/P1合成规则与短结构化输出提示，W07 | 测试case答案、整套人格散落在工具代码 |
| adapters/ | catalog/profile/knowledge/memory/task/research/media副本适配，W04 | 直接加载生产env、把not_found改成complete |
| transport/ | 唯一sink调用与segment回执，W01/W05 | 自主选话题、依据生成成功声称已送达 |
| fixtures/ | 用户事件状态机和公开输入，W06 | 手写本次被测助手台词 |
| evaluation/ | E0、覆盖、事实/状态/质量检查，W03/W06 | 被worker读取、改变运行输出 |
| tests/ | M/X变异及E2确定性合同测试 | 独立假检查器代替正式验收路径 |

provider gateway属于controller管理的独立进程，凭据只在网关；loop经受限接口调用，不读取源DB取密钥。oracle保存在worker不可读的评估挂载目录，不能只靠约定“不打开”。

旧scripts/lab_*只作为历史参照，不调用它们产生新正式成绩。确需复用纯函数，应复制到明确实验模块、保留来源与hash并执行合同测试；不得因import把生产计时器、配置加载或写入带进来。

默认不直接import工作台feishu-sync-server.mjs：该模块会加载原env。应对冻结导出实现本地定向查询适配。确需测试原工作台行为，仅在独立LIVE-READONLY集成进程或完整复制且受限的实例进行，不能绕过第3节边界。

### 15.2 所有事件的公共主路径

~~~text
cli前置阶段验证
  → controller启动受限worker
  → input校验owner / kind / virtual_time / event_id
  → store读取状态并处理去重、当前版本
  → context组装底座、当前状态与可发现目录
  → loop调用真实模型，形成或续接动念与动作
  → contracts校验结构、引用、owner
  → policy校验本动作权限、版本、能力和预算
  → 按动作进入下面唯一分支
  → store提交实际结果、trace追加证据
~~~

输入kind固定为user_message / opportunity / task_due / tool_result / delivery_result / silence_observed。类型由入口来源赋值，不由模型伪造。事件ID去重、owner验证等无语义操作可在模型前执行。不得给同一事件同时跑旧主动调度和实验loop。

### 15.3 分支选择与执行顺序

| 分支 | 触发及语义决定者 | 执行路径 | 结束/续接与禁止行为 |
|---|---|---|---|
| P01 明确工作查询 | user_message；模型理解实际问题 | context → loop输出查询动作 → adapters定向读取 → tool_result回同loop → ready文本 → sink | 必须响应当前请求；不先做无关主动评估，不受角色“正在上课”禁用 |
| P02 工作讨论/建议 | user_message或业务机会；模型决定所需资料 | 查背景/约束 → 同loop讨论假设 → 交付或必要补问 | 无执行回执只能说草稿；不把所有工作词都当查数 |
| P03 纯情绪/个人交流 | user_message；模型理解倾诉、调侃、关系话题 | 当前人格/关系状态 → 同loop个人动作 → sink | 可延续动念；不能默认查业务，更不能抛经营问卷 |
| P04 工作+情绪混合 | user_message含实际工作请求 | 同P01/P02完成工作 → 同一交付保留适度情绪回应 | 不强制分两次生成；不能只安慰漏答，也不必加调情 |
| P05 自由主动机会 | opportunity；模型依据上下文选动念 | 形成/更新候选 → 选text/tool/media/wait → 相应分支 | 题材不能由fixture或时刻硬选；预算/窗口另由policy约束 |
| P06 到期承诺/日报 | task_due来自真实复制或隔离创建任务 | 核对任务版本/未完成 → 获取需要的事实 → 交付 | 优先履约；无当期数据如实说明，不能旧数据充日报 |
| P07 知识补问 | P02/P05中识别影响判断的未知 | 先查 → 问题与动念关联 → sink → awaiting_user | 已有资料不问；不为填字段机械生成题目 |
| P08 知识回答 | user_message；模型判断是否回答活跃问题 | 引用原问题 → 暂定候选 → 更新有条件判断 → 按权限确认 → 后续复用 | 嗯/调情不是确认；候选状态不能偷偷转confirmed |
| P09 研究与经营灵感 | 模型选research动作 | 限定问题/日期/范围 → research结果 → 同loop形成适配建议/任务 | FROZEN标归档研究；LIVE标真实搜索；无来源不称最新 |
| P10 图片准备 | 模型选media.prepare动作 | 同intention+情节引用 → planner → provider资产 → tool_result回loop | 图可用不强制发；失败同目标改策略，不能另起照片动念 |
| P11 图文交付 | 同loop选择已prepared资产交付 | policy → transport分别送图/配文 → 分段回执事务 | 图生成≠图送达；partial不算全部完成 |
| P12 等待/静默准备 | 模型wait或窗口未开 | 保存等待条件/准备结果 → 退出本事件 | 不送消息，不定时忙轮询；下一合法事件再评估，不能永远wait规避任务 |
| P13 工具失败 | adapter返回明确错误 | tool_result → 同loop解释/合法重试/挂起 | 不拿HTTP200替业务status；不伪造数据、不用生活借口替错误 |
| P14 投递失败/未知 | transport实际回执 | store分段记录 → 按幂等键查询/恢复 | 不让模型把unknown猜为delivered；不重复已送段 |
| P15 沉默观察 | 已送达且经过配置时间，controller虚拟事件 | store记录观察 → 下个合规机会模型修订策略 | 不记录拒绝/喜爱；已完成查数不因没回复变失败 |
| P16 业务插入与个人恢复 | 新user_message使当前动作版本变化 | 旧动作挂起/失效 → P01/P02 → 用户/机会再触发恢复判断 | 不自动发送准备中的旧图；重新核时效、边界和目的 |
| P17 明确暂停/拒绝 | 用户明确边界；语义理解加状态约束 | 保存作用范围 → 取消相关ready发送 → 合法新话题或等待 | 只拒某话题不等于全局停止；全局安静不得继续个人主动 |
| P18 重启/并发 | controller恢复或多个事件争版本 | store事务/CAS/lease → 恢复未决动作 → 幂等回执核对 | 不重造ID，不用旧结果覆盖新答复，不以重启清空额度 |

P01–P18为执行路径编号，只用于路由日志/覆盖评估；不得把编号或“本场应该选择某路径”注入模型。工作/个人的语义选择由模型决定；授权、时机、版本和事务由代码执行。测试控制器只能提供真实事件及能力条件，不替模型做决定。

### 15.4 动作分流的硬合同

- action=tool：必须存在工具执行记录；tool_result以结构化证据续入当前线程，不伪装成用户说话。返回后允许继续工具，但受6次模型/4轮工具预算。
- action=deliver：只接受当前版本ready内容及可读资产引用，调用唯一transport；不能直接append一个“sink://”字符串就当有回执。
- action=wait：记录reconsider_condition和关联线程，结束本事件；不给表达模型再加一句“还是发点什么”。
- action无效/未知：schema_failure并保留原响应，不套固定查询补救，不把它归为“无机会”。
- 窗口关闭：可保存prepared，禁止发送；下一窗口不能直接发旧结果，必须核对用户版本、资料/素材有效期。
- 新用户输入：发送前版本检查优先于旧主动动作；已发送内容不能撤成“没发”，据实际回执续接。
- 确认知识：按权限由工具事务实现，模型只能请求；拒绝确认仍可明确按用户本轮说法讨论，不假装正式入库。
- 完成任务：使用交付验收与实际回执更新；不能由模型单独输出operation=complete就完成未执行任务。

### 15.5 每条路径的定位证据与强制测试

trace增加path_id、entry_kind、callsite（模块/函数）、intention/action/event/owner/version、branch_reason_ref。branch_reason_ref引用短决策依据或policy规则，不能由报告者事后猜路径。每条工具记录parent_action_id、原参数、规范化diff、result_id；每条sink回执引用segment_id。

W06输出path-coverage.json：P01–P18映射到原A/B/C/D/R/I具体分支，列正常、失败、恢复三类适用情况和证据。不存在恢复含义时写理由；不得空白。

至少有以下路径守恒测试：
1. 同输入模板改店/日期/指标，实际工具参数跟模型返回变化（X09）；模型不调用时不能出现请求（X10）。
2. 明确工作→个人→同工作续接，线程/资料owner不串；照片准备→工作插入→恢复沿P10/P16/P11。
3. 知识查询已有/未知/用户短答/明确回答/确认拒绝各支，最终候选状态与建议变化可回查。
4. 研究成功/无结果/过期、图片成功/失败、文本/图文partial/unknown都进入规定错误路径。
5. 自由机会选text/tool/photo/wait都可由真实模型产生；注入动作只证明执行路径，不能替代自主选择样本。
6. 全局暂停、局部拒绝、窗口关闭、预算耗尽均从实际policy拦截，不通过修改模型输出“假装没想发”。
7. 冷启动不读共享历史，真实关系回放不重置历史；两组路径和初态明确区分。

正式版本启动时校验依赖方向：runtime不能import fixtures/evaluation/export；adapters不能import controller秘密加载；除了transport不得生成delivery receipt。静态依赖检查配合X07/X08真实边界探针，任一失败禁止W07。

### 15.6 改错位置时的处理和交接提示

发现问题先按“源→副本→上下文→模型动作→工具→状态→回执”定位最早偏差。源有副本无改export/parity；副本有模型不可查改context/adapters；模型选对执行错改loop/adapters；动作正确却状态错改store；内容被后处理破坏改交付路径。不能到人格提示词里补“请一定回答”掩盖这些故障。

W00交接检查必须向执行者展示：实验根路径、唯一CLI、各组件文件、P01–P18路径图、原生产对应模块仅供参考。若想调整上述归属，先写设计差异及影响测试，不在开发中悄悄新建旁路。本轮任何生产集成、上线或真实Agent执行均不在这些路径的授权范围。
