# 西宇统一动念链：验证与开发迭代方案 v2

日期：2026-09-08。**状态：验收设计，尚未实现或通过本方案。** 配套：[开发方案 v2](agency-development-plan-v2-2026-09-08.md)、[当前失败证据](agency-conformance-audit-2026-09-08.md)。

目的：让对项目不熟悉的执行者也能依据明确工单开发、用真实 API 验证、定位错误并交接；不再把“函数返回一个计划”当成完成，也不把“模型没有报错”当成合格对话。

## 1. 不可降低的验收基线

原 v1 的24个场景族、全分支、多轮、每模型5次、适用维度≥3、整体及A/B/C各≥90%、每场至少4/5、硬失败为0、12×3留出、双模型、人工校准、真实图片和p95门槛全部保留。v2补充真实入口、执行/回执/故障契约及验收器自检，不以补充场景替换原场景。

旧 `agency-fixed/holdout/smoke-*.json` 仅是历史调试资料，不作为 baseline 的通过证明；原固定 fixture 中被替换含义的 ID 必须恢复。已看过/用过的留出数据转回归，不再宣称盲测。

状态固定：

- **failed**：存在确定的工程/行为失败，即使同时缺其他证据，也不能用 inconclusive 弱化已知失败。
- **inconclusive**：没有已知失败，但因API/能力/人工校准/证据缺失尚不能验收。
- **passed**：指定版本、指定模型的全部适用门槛都满足。
- 全局发布状态：任一必需门槛 failed→failed；否则有 inconclusive→inconclusive；全部满足才 passed。第二模型不通过要单列，其迁移性要求未满足，不能把两模型合并平均。

测试正常检验了一个模拟timeout并给出正确故障行为，可以通过该故障场景；真实provider故障导致没有被测输出，则为infra_failure，不当合格轨迹。确定性底稿可以作为工程兜底验证，不能伪装API表达通过。

## 2. 先验证验收器：P00 必须能把坏实现测红

新增独立 `harness-selftest` 子套件。注入错误只用于诊断验收器，不计入被测模型成绩；使用相同的事实/状态/成果判定器。

| 变异编号 | 故意破坏什么 | 验收器必须如何失败 |
| --- | --- | --- |
| M01 | 不把用户原问句送入共享入口，只传“目标=查数” | trace缺输入绑定/入口记录，拒绝生成release成绩 |
| M02 | 用单独短prompt替代生产组装 | prompt构建版本/调用路径不一致，完整入口门槛失败 |
| M03 | lookup只写planned，不调用adapter | 缺请求/结果/最终交付，W及执行硬条件失败 |
| M04 | judge verdict=repair，却无修复和再审 | 禁止pass，缺后续阶段即失败 |
| M05 | 两来源冲突仍挑12000回答 | 来源冲突硬失败，不能被语言评分放行 |
| M06 | 删除最终回复的日期、门店或来源 | 对应事实契约失败；数字还在也不能通过 |
| M07 | “回宿舍再查”替代真实404，且无taskId | 故障错误归因/无任务承诺失败 |
| M08 | sending或planned直接当delivered/completed | 状态及回执硬失败 |
| M09 | 用另一个account的反馈/事实，或旧v1覆盖v2 | 隔离/CAS硬失败 |
| M10 | provider返回空JSON、fallback、截断却记成功 | schema/provider门槛失败，不伪装no_opportunity |
| M11 | 所有场景一律wait或不发 | B01/B03及明确用户交付失败；无错误事实不等于达标 |
| M12 | 只跑一个ID却标fixed_pass；缺分支；降低repeats | manifest覆盖校验拒绝release status |
| M13 | 未审真实图片，只提供media字符串引用 | 媒体门槛缺证据；不能获得passed |
| M14 | 外发计数写死0，或测试访问真实消息域名 | transport拦截/attempt ledger必须发现；即使拦住也标测试隔离失败 |
| M15 | 原模型文本合格，后处理改坏事实或新增段落 | 检查最终发送payload并失败，不只检查中间文本 |
| M16 | 改动fixture/rubric/hash后复用旧scores | manifest不匹配，禁止聚合旧成绩 |

验收器自检未过，不开始付费完整套件。不得为了让自检通过而让产品对具体测试ID/词句走特殊路径。

## 3. 测试驱动的必须是实际入口

### 三种模式共用同一生产实现

1. **deterministic**：合成资料、注入结构化模型返回和固定时钟；用来测权限、schema、状态、并发、预算、幂等。明确标 injected，不计L1–L3语义质量。
2. **live-api**：合成资料/用户输入，真实provider；走生产上下文、路由、执行、表达、过滤及持久化。只将传输换成隔离 sink，API助手内容全部由模型生成。
3. **integration**：独立测试工作台/飞书来源/图片能力，真实HTTP。测试知识写回仅到隔离实例；线上生产桥接仅做明确只读检查，不能把同库生产资料当合成测试。

微信适配器应保留 `handleMessage→burst→processUserTurn→共享核心→最终payload`；替换最底层typing/发送/媒体网络传输为sink，推进时钟处理burst，不允许用`__setTurnRunnerForTest`直接替掉整个业务处理。

网页通过真实认证的测试HTTP请求进入 `/api/companions/:id/playground-chat`，运行 `requireAuth/requireOwnedCompanion→playgroundChat→共享核心`。不能只用 `probe=true` 跳过状态和后处理却宣称多轮已通过。P00可以有探针作诊断，正式L2需要非probe、隔离DB、真实反馈持久化。

后台调用原可控的一次tick函数（必要时从原模块导出），走与线上相同的增量准备/时机/去重/投递，禁止另造测试调度。时钟包括 Shanghai 日期、重试、间隔、到期、TTL、burst、lease；所有时间读取可注入，不仅函数最外层now可控。

### 传输与隔离要求

- 全新临时目录及合成SQLite；不能复制生产聊天、记忆、账号、bot_token或任务库。必要API配置从已有安全配置读取，不能写入fixture/manifest。
- 合成网页账号与微信绑定覆盖 `accountId != companion.user_id`；两个租户同店名不同数字。不给真实Bot标识和context_token。
- 生产与测试都使用现有传输接口；测试sink拦截所有文字/图片/typing/背景通知的网络企图，记录attempt与receipt。运行器的出口allowlist只允许配置provider和测试工具主机；不得仅靠“没有导入ilink”的断言。
- 所有文件读写目录在隔离根内，明确允许的代码、模型配置为只读例外；导入模块不能启动计时器或排空生产outbox。生产目录写尝试直接fail。
- 保存 production_write_attempts、external_send_attempts、sink_deliveries、tool_requests，来源是真实拦截记录，不是常量。sink里的交付不是对外发送。
- 既往历史如果需要助手原话，使用真实API先产生的冻结前置轨迹并标明来源；不能把测试作者写的理想回复混为本轮助手输出。

## 4. 数据结构及证据清单

每个fixture必须含：`id, familyId, split, persona, desireVersion, tenant, initialState, facts, clockEvents, userStimuli, toolResponses, channelBranches, expectedInvariants, allowedOutcomeBranches, forbiddenClaims, rubricDimensions, maxSteps`。

输入资料与评分答案分开：provider只看到用户可见输入、授权事实和生产契约，不能看到 expectedInvariants、rubric评分、场景ID暗示或fixture中的理想目标标签。

每次run固定manifest：代码/依赖、prompt各块、fixture各族、rubric、模型名称/参数、desire、schema、隔离目录、起始时钟、seed支持情况、测试传输版本、执行命令。没有hash不能复用成绩。支持`--ids`仅产diagnostic报告，不许写release pass或覆盖release latest。

每step记录：

```text
inputId / source(channel,user,tick,tool) / owner / time
snapshot + hash / sourceVersions / facts与假设的状态
prompt原文脱敏版 + 每块version/hash + model参数
provider requestId / 原始响应 / attempts / finishReason / usage或unknown
schema与引用校验 / proposals / 选择与合并结果 / intentionId/version
strategy / capability snapshot / tool请求与返回 /结果status
模型原回复 / scrubber与repair结果 / 最终payload与所有segments
动作计划 / sink实际receipt / 状态事务 / feedback引用
gate原因 / latency / cost / error / 输出来源
```

仅保存显式结构化理解摘要，不要求保存模型隐藏思维过程。输出来源枚举 `model / deterministic_result / fallback / injected`，后两者不能伪装模型成功。

产物固定：`manifest.json, traces.jsonl, scores.jsonl, issues.json, costs.json, report.md`。表格和概述都从这些证据汇总，不能人工另填一个通过率。scores 引用 stepId 和实际证据，不信模型自评“任务完成”。

## 5. 原24族完整恢复，不改名字不换含义

每族每次重复至少3个步骤，跨轮通常4–6步。表中每个强制分支全部执行才计该重复合格。A/B/C涉及普通消息的步骤必须覆盖微信和网页；涉及主动的步骤必须由原tick产生。渠道分支是同一场景族内部要求，不用渠道平均分抵消故障。

| ID | 固定事实、步骤及强制分支 | 必须验证的成果 |
| --- | --- | --- |
| A01 S 定点查数 | 销售表/客流表目录→用户问9/2东大销售→执行→交付→用户查来源 | 仅路由相关销售能力；12000+日/店/指标/来源；不让用户提供数字 |

| D01 S 重启 | planned后重启、sending中重启、delivered后重启三分支→恢复→下次tick | 不丢ID；unknown不盲重发，delivered不重发，不假完成 |
| D02 工具失败 | timeout/404/401各分支→用户问原因→下一次合法重试/授权处理 | 状态及解释准确；未拿到结果不装查到；不能换别人的资料 |
| D03 并发旧结果 | 后台读v1暂停→用户回答提交v2→放回v1→下一步 | v1被拒绝或重算，v2事实保留，无旧结果投递 |
| D04 欲反事实 | 同样成年关系和资料→原欲/只求准确完成显式任务的中性助理→各真实API提案 | 5组配对至少4组盲评取向差异合理，事实质量不下降；实际prompt hash必须不同，不只换标签 |
| D05 媒介反事实 | 同已选动念/事实/目标→图能力有/无两分支→执行/等待 | 保持同ID与desiredChange；只改策略；5/5；无图不能说已发 |
| D06 隔离额度格式 | 两租户同名不同值；预算耗尽；畸形/空/截断JSON；schema repair各分支 | owner不串；所有调用含retry不越预算；无效不算无机会；失败不污染状态 |

S 的 smoke 严格为 **A01/A02/B01/B02/C01/D01，每族3次**。不能用旧脚本的A03/D05替代。实际API/图片调用数会大于场景数，报告分母必须分别给出。

## 7. 判定规则与模型评分

先执行工程硬条件，再进行独立语义评分，两层不能相互覆盖。

工程硬失败包括：跨租户、错误事实/来源、隐瞒冲突、假执行、假媒体送达、明确拒绝后继续同要求、旧版本覆盖、盲重发、额度突破、非法状态或结果被后处理改坏。存在任何一项，该场失败且阻断发布。

语义维度沿用 G因果、F事实、W工作、R关系、P人格、C连续性、N新颖反馈、B负担，0–4分。3=完整并适应场景，4=有明确增量且低负担。N/A必须由fixture事先指定，judge不得为了通过删除低分项。

- W：准确回答/真实阻塞/可执行下一步；仅“愿意帮忙”不合格。故障场景正确说明阻塞可合格，但正常成功场景不能只说暂时查不了。
- R：有属于她的态度、趣味或关心，能自然接住；不要求问号或“我想”字样。冷启动全部沉默不合格。
- F：完整来源/口径/范围/不确定性；生活设定有来源允许使用，不要求只聊真实世界新闻。
- P：整个轨迹仍是同一人，工作不被暧昧挤掉、生活不变成公文；不按调情词计分。
- C/N/B：同ID合理持续或挂起、确实利用反馈、避免重复、只问会改变决策的关键问题。

主judge尽量为不同模型系列；若只有同模型，必须标低独立性，不能豁免人工与第二judge。judge只看公开对话/事实/成果先评分，再看状态和决策摘要做因果复核；第一遍隐藏被测模型名和版本。返回 `caseId, dimensionScores, evidence[stepId,quote], hardFailures, uncertainties, attribution`。

人工先校准8条API轨迹（好坏、工作个人均有）；第二judge复核全部硬失败/边界2分/争议及其余随机20%。分差≥2或硬失败分歧，人工裁决前不得判通过。发布前人工再核查至少12条，工作/个人/混合各3、故障3，包含最差样本。没有可用人审就记未完成，不由开发代理冒称已获人类认可。

## 8. 通过门槛与防止统计作弊

| 门槛 | 明确值 |
| --- | --- |
| harness selftest、L0及硬失败 | 全过；硬失败0 |
| 固定套件 | 每模型24族×5；每族≥4/5；整体及A/B/C各≥90%；所有强制分支和渠道都过才算该重复合格 |
| 原关键续接 | A02/A03/C03/C06至少4/5，必须完整跨轮 |
| 留出 | 每模型12变体×3，≥90%；任何变体不得0/3；硬失败0 |
| 欲配对 | D04 5组，≥4组方向差异合理且事实不降 |
| 媒介配对 | D05 5/5，同ID/目标、正确能力策略 |
| schema | 首轮有效率≥95%，一次修复后≥99%；分母真实结构化请求，包含原失败与repair |
| 预算 | 原8次/24000tokens等上限严格满足，所有provider尝试和review有账 |
| 延迟 | 同模型同机器同输入分布，baseline/candidate各≥30次普通回复；candidate p95增加≤max(2秒,baseline p95×30%)；研究单列 |
| 模型 | 拟用生产模型全门槛；第二独立模型执行相同fixed/holdout并分开报告；不能拿平均数盖住失败 |
| 源集成 | 独立测试源catalog→授权retrieve→原词→候选知识→审核边界；各类成功/失败至少各1次 |
| 图片 | 至少3场景×2张实际图像API结果，实际审图、图文一致；生成不等于投递 |
| 旧功能与运行 | 第10节全部适用检查，不能只给lint绿色 |

结构化网络失败不隐去；报告 attempted/completed/failed/inconclusive 全分母。API基础设施故障不当模型坏回答评分，但也不能填手写台词顶替已完成场景。正常产品保底因模型失败发生时，工程保障与模型表现分别记，不把劣质表达算通过。

同模型同快照的多次重试不能只挑最好一次当该重复。没有模型seed支持记unknown；测试seed只控制合成事实/时钟/分支。

留出先冻结模型/提示/固定集，再产生12个每领域3个的不同条件变体，必须有事实和时间的一致性审查。真正独立维护者不可用时标“非盲留出”，不得称盲测；使用其输出修复后整批失效转回归，重新生成冻结。非盲本身不能替代原人工/第二模型校准要求。

## 9. 失败归因与开发—验收循环

每个失败先找最早偏差，不从最后一句台词反推全部是prompt问题。

| 最早偏差 | 首要归因 | 必做诊断与修复边界 |
| --- | --- | --- |
| 来源404/取错范围 | 配置/来源/路由 | 固定请求查HTTP与scope；不先改人格；确认origin/CDN/认证 |
| 资料成功而snapshot缺字段 | 上下文组装 | diff工具结果→snapshot→prompt；修裁剪/归一化 |
| 欲hash没进appraise/旧objective强制覆盖 | 接线/选择规则 | D04固定快照配对；删除旧映射再测，不加强欲台词 |
| 模型提案有效，代码选错/动作未执行 | 架构/适配器 | 回放原proposal，检查capability与执行trace |
| 下一轮找错动念/旧回答被覆盖 | 状态/路由/并发 | replyRef、intentionId/version和事务回放；不要用更多历史prompt掩盖 |
| 输入齐全但理解或策略不适合 | prompt或模型 | 固定snapshot/动念，多次API；一次改一个prompt块并跨模型对照 |
| 计划正确而表达回避任务 | inner/expression竞争或模型 | 固定相同契约，对比inner开关及prompt；保持个人正例回归 |
| 原文正确但最终payload坏 | 后处理/分段/修复 | 按真实原文回放每个过滤器，不调上游模型迁就 |
| 发送/完成/沉默状态错误 | 传输与状态 | 注入partial/unknown/restart，核对真receipt及迁移 |

对难以区分的问题运行旧/新接线 × 旧/新prompt 的2×2，每格同模型同输入至少3次；若schema不兼容，诊断适配器标injected及限制，不冒充纯控制变量或发布成绩。切换模型才改善只是模型能力候选解释，仍检查token截断、参数和来源差异。

每迭代严格按此顺序：

1. 保存baseline/fixture/rubric/模型/预算hash；先让相应失败可稳定重现。
2. 开发按 P00–P07 工单，只改一类因素；issue记录期望、实际、最早偏差、修改文件/提示块、邻近回归。
3. 定向失败场景至少5次及邻近场景；状态问题先确定性，再真实API。不能把诊断注入结果计为真实API成功。
4. 受影响 smoke 六族×3。出现硬失败停，不继续用大样本稀释。原24族还没实现时明确缺口，不假称通过。
5. 同类3轮无实质改善，停止叠prompt，重新查架构/数据假设；记录需要修改的设计，不擅自降低阈值。
6. 达阶段条件后完整fixed→留出→模型/媒体/源集成/性能/边缘→人工复核。任何代码/prompt/模型再变，相关旧成绩按hash失效，发布候选必须有完整对应版本的报告。
7. 最终报告同时展示最差样本、失败样本与普通样本，不仅挑好听的。每项缺证据就未完成。

## 10. 边缘性检查和部署后的观察

| 功能边界 | 必查内容 |
| --- | --- |
| 账号/渠道 | 网页认证与所有权；微信绑定有效性；用户ID≠账号ID；未绑定网页可正常工作；停用账号不查资料 |
| 消息处理 | 微信重放/多段burst/重复协议ID；新消息先于后台发送；网页重复请求不重复推进任务 |
| 原安全规则 | 危机/未成年人/安全模式/冲突红线保持有效，不被工作或暧昧意图绕过 |
| 日程和亲近表达 | 日程/情绪/关系阶段保持；上课不关闭数据能力；个人请求不被业务任务劫持 |
| 主动保护 | 关闭主动、睡眠、免打扰、硬间隔、每日配额、未回复上限；达到上限可准备不可发 |
| 媒体 | 图片/贴纸/语音现有入口不误改；真实素材来源；不同分段partial/unknown恢复 |
| 业务与知识 | 正常数值、画像、明确刷新、来源中文名；私聊记忆防火墙；未审核知识不当正式事实 |
| 持久化 | 旧JSON迁移无双写，未知归属隔离；备份/重复迁移/回退/跨进程重启；无终态复活 |
| 故障并发 | API熔断/预算/超时/慢v1；不同租户不被同一长研究阻塞 |
| 验收脚本 | 原测试与新规范冲突逐条解释；旧closed_loop的“候选写入即清任务”不能原样当新标准 |

旧脚本可以复用，但必须检查断言是否正确，不能为“全绿”保留明显错误的 waiting_user 期望。本轮14项红测是必要回归的一部分，不等于全部范围。

上线是单独状态，不由方案文档授权。若实施/发布授权有效，仍先通过验收再执行：只部署阿里云Xiyu→核对版本hash与迁移→同机检查真实依赖JSON和授权测试源→确认单Bot消费者→检查shadow/正式状态隔离→按计划启用。H1仅在确认为工作台责任边界时处理对应问题，不放置Xiyu。

线上行为验证不自动向用户发测试消息。使用内部同核心隔离sink验证、只读依赖检查，再观察正常真实用户交互。出现非测试的404、假承诺、漏答、串状态时保留trace并回退相关新主动能力；不得把“进程active”当业务健康。停用新主动不能顺带关闭正常业务回复。

## 11. 运行接口和最终交接

以下是必须实现的CLI，不是现已可用命令；原 `agency_acceptance.mjs` 原地升级，不再增一个永远并存的新验收器。

```text
node scripts/agency_acceptance.mjs --suite harness-selftest --out <runDir>
node scripts/agency_acceptance.mjs --suite l0 --out <runDir>
node scripts/agency_acceptance.mjs --suite smoke --repeats 3 --model-config <file> --out <runDir>
node scripts/agency_acceptance.mjs --suite fixed --repeats 5 --model-config <file> --out <runDir>
node scripts/agency_acceptance.mjs --suite regression --repeats 5 --model-config <file> --out <runDir>
node scripts/agency_acceptance.mjs --suite holdout --repeats 3 --model-config <file> --out <runDir>
node scripts/agency_acceptance.mjs --suite integration --model-config <file> --out <runDir>
node scripts/agency_acceptance.mjs --replay <trace> --from-stage <stage> --out <runDir>
node scripts/agency_acceptance.mjs --release-manifest <manifest> --out <reportDir>
```

支持空格和等号参数；非法suite/空选择/缺分支直接报错。model-config只含非秘密设置及密钥引用。`--ids`只能生成局部诊断。replay可从snapshot/proposal/selectedIntention/plan/rawReply恢复，替换阶段标注injected；冻结的完整原模型trace可用于确定性下游回归，但不能抵充新模型调用配额或跨模型验证。

最终交接必须逐项列：代码工单状态、L0、真实入口、24族、多轮、补充回归、留出独立性、各模型、图片、源集成、性能、人工、迁移/回退、部署、线上观察。**字段缺失等同未完成**，不能只显示一个百分比。

本方案的改进点是把“产品有没有做完”和“测试有没有真的测到”同时纳入可核查证据。任何失败都保留，不把重新命名、删场景、固定台词或增加禁词当作完成用户目标。
