# 企业知识路由与企业认知地图（本地实现）

日期：2026-09-06。取代上一轮以周报异常为中心的知识补全策略；保留原候选审核、隐性知识存储、上下文编译与主动时机闸门。

## 本轮解决的实际问题

1. 溪语以前只检索本地记录，工作台虽能读取飞书来源，聊天查询却没有接上。现在按小型能力目录选择来源，读取确切日期和门店的事实。
2. 旧缺口主要重复周报未解决问题。现在企业知识建设由明确的知识地图驱动；历史经营问题独立保留，不再进入企业知识主动提问主线。
3. 人格生成有时只问“头疼了吗”，未询问原知识问题。新增内容校验：开场允许人格表达，知识问题必须保留；重试仍不满足则不发送、不标记任务已投递。

## 一、查询架构

流程：用户原话 → 现有 AI API 判断生活/工作/混合及 lookup/explore/support/delegate → 小型能力目录与授权门店 → 服务端校验日期、门店、指标 → 单一来源适配器 → 程序计算、完整性校验 → 带来源口径的事实 → 人格表达，数值仍受确定性保护。

生活对话不会读取飞书。讨论、建议和周汇总继续走原上下文检索；明确单日查数走来源路由。路由模型只能提出语义参数，具体凭证、页签、字段映射、权限验证和加总都由服务端执行。对明确的“销售额”只读销售额，忽略模型顺带提出的其他指标，避免过取。

| 能力 | 实际来源 | 可查数据 | 粒度 |
| --- | --- | --- | --- |
| channel_daily | 运营渠道日销售来源表 | 销售额、销售票数、实收、线上/线下销售额 | 日期 × 门店，汇总其配置渠道 |
| daily_traffic | 周报复盘辅助表 v3 的录入客流页签 | 大盘客流、触达人数、转化人数 | 日期 × 门店 |

新增来源通过适配器登记用途、粒度、指标、日期列、门店列、页签和口径。不是让模型看到某个文档链接就自行遍历它。当前没有承诺任意飞书文档、任意指标自动接入；无结构的文件问答需要另加文档检索适配器。

### Token 与读取预算

- 给模型的是能力元数据和少量事实，不给全表内容。直接查数不再先拼接全企业上下文。
- 初次每个选中页签读取表头、单列日期索引、命中行；日期索引内存缓存 5 分钟，行值每次重读。
- 单次限制一个来源文档、最多 8 个页签、24 次请求、每页签日期索引最多 5000 行、同日最多 4 个候选行。超预算报限制，不伪装为无数据。
- 飞书会返回填充空白行；已修复将填充行误判为超过预算的问题。
- 当前日查询一次支持一个门店、一个有效日期。区间明确但未支持时澄清，原周查询继续走本地周数据。没有年份按当前中国日期的年份解释，答复展示完整年份。
- “东大”未配置为别名时明确询问是否指“东坝”，不因模型猜了 DONGBA 就直接读错店。
- 完整性要求每个配置渠道都有唯一来源行且目标指标不是空值。缺行、空值、重复行不当成 0 或全量合计；接口异常不回退到其他日期。
- 日期索引缓存可能使刚新增的日期最多延后 5 分钟可见；同一已存在行的数据更新每次直接读取。尚无跨页签原子快照，来源在查询期间更新时不保证事务一致。

### 真实读数验证

实际 AI 路由及飞书 API 测试：2026-09-02 东坝销售额 266 元，开店宝 168 元、小程序 98 元，其余三个渠道各 0。新查询读取五个页签的第 27 行，原有 source-preview 独立读取并加总结果同为 266。口径仅为已接入渠道全部商品销售额，不能声称是利润或所有未接入渠道的完整营收。

首次 15 次数据请求，缓存索引后 5 次。另一个飞书文档的 9 月 2 日东坝触达人数没有找到匹配行，返回 incomplete/null，未返回 0。

## 二、企业知识架构

核心对象不是“一个没解决的问题”，而是：企业/门店范围、知识维度、使用者岗位、已确认回答、来源、确认时间、关联任务和后续决策用途。

| 维度 | 支持的选择 | 主要了解对象 |
| --- | --- | --- |
| 企业定位与边界 | 哪些机会符合业务，哪些明确不做 | 负责人 |
| 目标与取舍 | 收入、利润、增长冲突时如何选择 | 负责人 |
| 岗位目标与协作 | 各岗位要什么结果、期限和配合 | 所有岗位 |
| 客户与购买理由 | 为谁改产品、改表达或服务 | 运营、市场、门店 |
| 产品与价值承诺 | 能卖什么、承诺到什么程度 | 运营、交付 |
| 财务与经营模型 | 预算、利润、现金流底线 | 财务、负责人 |
| 资源与交付能力 | 人手、设备、时段能执行什么 | 门店、运营 |
| 权限与流程 | 谁拍板、如何批准和交接 | 负责人、人事 |
| 渠道与合作资源 | 什么关系及触达资源真的可用 | 市场、运营 |
| 品牌与舆情边界 | 什么认知要维护、什么事件升级 | 品牌、门店 |
| 数据来源与口径 | 怎样核对方案效果 | 财务、运营 |
| 有效做法与失败边界 | 哪些条件下可以复用经验 | 所有岗位 |

七类岗位：负责人、经营运营、品牌舆情、市场曝光、财务、门店交付、组织人事。维度定义集中在 knowledge-map.mjs，可扩充，不依赖周报字段。

### 调度如何工作

1. 从知识地图计算每个维度是否有对应范围的确认记录，待审核答案不算已记录。已有档案继续作为提问上下文，不自动把档案存在当作整维度已掌握。
2. 先选没有前置依赖的企业定位；确认后开放目标、客户、产品等。财务边界依赖目标，产能依赖产品，权限依赖岗位目标。按角色相关性排序，每次最多 4 个（上限 6）。
3. 程序拥有选维度和依赖关系的权力。API 模型只结合已有档案将选中维度具体化为易回答的问题；不能把任务替换成旧周报异常。模型不可用仍可用地图里的基础问题；无新可选维度时不调用模型。
4. 人工点击“规划下一块知识”，或现有溪语主动机会触发规划。后者仍遵守 24 小时发现冷却及数据指纹、原20小时知识检查和生活/睡眠/配额限制。没有新增独立定时任务，也没有开启原本关闭的主动策略。
5. 企业建设任务和历史经营问题分流；历史记录不删除。旧待投递历史问题在下一次事件刷新时退役。仅企业知识、适合向人了解的任务进入此主动提问路径。
6. 用户可在知识地图任务下填实际情况，或回答溪语问题。候选进入原待确认信息；审核应用后归入对应知识维度，回写范围和岗位，再供检索、灵感和方案使用。
7. 相同范围、维度去重；岗位目标额外按岗位区分。东坝答案不能令中影或全企业范围自动变为已记录。

### 已实现与边界

当前已升级为企业知识地图 v2。12 个维度继续作为顶层索引，每维拆成三个或四个分析切面；确认回答只覆盖其关联切面，维度状态使用 `unknown / review_pending / partial / decision_ready`。历史没有 `facetId` 的确认知识保留为该维度的未分类部分记录，不会错误地令整维完成。

依赖维度达到 `partial` 后即可开放后续相关维度，避免为了补齐整张问卷堵住真实工作；同时仍会继续生成该维度下一个未覆盖切面。模型必须原样返回程序选定的 `dimensionId` 和 `facetId`，并做答案摆动测试：合理答案不会改变建议、执行边界或验证方法的问题不值得占用用户注意力。

本轮按用户允许的初期假设：当前交流对象能够了解这些问题。已记录适合回答的岗位，并提供手动角色视角；还没有按员工账号绑定岗位、核验其知情范围或跨员工转派询问。角色视角不是访问权限替代物。

角色目标和维度信息随确认知识进入上下文；没有将所有岗位重新统一成营收目标。现有每日经营建议本身仍偏运营，不能据此宣称已经实现完整财务助理、舆情监测或所有岗位的专用业务流程。

## 三、验证与证据

- backend/cognition/knowledge-routing-smoke.mjs：日期、歧义、生活不取数、两来源选择、按行读取、索引缓存、缺失不是零、知识依赖和岗位/门店隔离。
- scripts/check_enterprise_routing.mjs --live：隔离 SQLite 与 runtime-state，真实语义 API、两个实际飞书来源；知识回答→待审核→应用→地图→下一维度。
- scripts/check_enterprise_closed_loop.mjs：按新企业知识契约更新，检查拒绝重开、部分回答、幂等、主动任务顺序、确认后复用。
- 同脚本 --live：实际模型生成问题、人格开场、情绪退出、回答提炼、审核、下一问题、灵感及 agent 交付。模拟答案仅写隔离副本。
- 连续性、延迟回复、上下文编译、前端只读初始化回归通过；保留上一轮同源读取与禁止缓存反写的修复。
- 浏览器检查知识地图、七类角色、企业/历史任务分流、规划按钮和回答入口。真实本地只生成了一条待答问题，没有替用户填企业事实。
- 证据：docs/validation/2026-09-06/knowledge-routing-live.json、knowledge-map-local.json；knowledge-map-live-before-question-guard.json 为发现主动开场漏问题的中间结果，不作该项通过依据。
- 修复后的完整复测：knowledge-map-live-final.json。实际开场保留了“东坝店目前主要服务哪些客群，有没有明确不做的业务类型？”；用户明确不想聊工作时回复陪伴并保留未完成任务。长交付内容仍有生成波动，回归通过不等于每份方案已获业务效果验证。
