# 溪语生产服务器 · 只读直连使用说明

> 面向**执行者**（人或 AI agent）。目标：让执行者自己连上生产做只读查询，
> 不再需要用户代跑命令、代贴输出。
> 本文档只讲只读访问。**任何写操作都不在本文档授权范围内。**

---

## 0. 一句话

用一把**免密的专用只读密钥** SSH 直连 `admin@39.106.153.59`，
全程 `BatchMode`（绝不弹密码提示），只跑只读命令。

---

## 1. 先确认你在哪台机器上

| 情况 | 做法 |
|---|---|
| **和之前的执行者同一台机器**（Windows，用户 `Administrator`） | 直接用现成密钥，跳到第 2 节 |
| **换了一台机器** | 必须自己生成密钥对，跳到第 6 节先做一次配置 |

⚠️ **私钥只存在于生成它的那台机器上**，不要拷贝私钥、不要通过聊天传私钥。

## 2. 连接参数（固定值）

| 项 | 值 |
|---|---|
| 主机 | `39.106.153.59`（= `xiyu.myworlds.cn`） |
| 端口 | `22` |
| 登录账号 | `admin`（**不是 root，永远不要尝试 root 登录**） |
| 私钥 | `%USERPROFILE%\.ssh\xiyu-readonly-nopass` |
| 对端 sshd | `OpenSSH_9.6p1 Ubuntu-3ubuntu13.19` |
| 主机名 | `iZ2zegvp8qr8jwkob665p2Z` |

**标准命令（Windows / PowerShell）：**

```powershell
ssh -i "$env:USERPROFILE\.ssh\xiyu-readonly-nopass" `
    -o BatchMode=yes -o IdentitiesOnly=yes `
    -o ConnectTimeout=12 -o StrictHostKeyChecking=accept-new `
    admin@39.106.153.59 "hostname; whoami; systemctl is-active xiyu-ai"
```

**标准命令（Linux / macOS / bash）：**

```bash
ssh -i ~/.ssh/xiyu-readonly-nopass \
    -o BatchMode=yes -o IdentitiesOnly=yes \
    -o ConnectTimeout=12 -o StrictHostKeyChecking=accept-new \
    admin@39.106.153.59 "hostname; whoami; systemctl is-active xiyu-ai"
```

**这几个选项一个都不要省：**

- `BatchMode=yes` —— 绝不弹密码提示。加上它，认证失败会**立刻报错返回**，
  而不是挂在那里等人输入。
- `IdentitiesOnly=yes` —— 只提供指定密钥，不把机器上其他密钥挨个试一遍。
  既避免误用别人的身份，也避免在服务器上刷出无谓的认证失败记录。
- `ConnectTimeout=12` —— 网络不通时快速失败。
- `StrictHostKeyChecking=accept-new` —— 首次连接自动记录主机密钥。

## 3. 只读边界（硬约束）

### 3.1 绝对不碰的目录与服务

| 项目 | 目录 | 服务 | 端口 |
|---|---|---|---|
| **溪语** | `/opt/xiyu-ai` | `xiyu-ai.service` | 3000 |
| **经营工作台** | `/opt/yuanqu-workbench-api` | `yuanqu-workbench-api.service` | 4175 |
| ❌ **LIMI** | `/home/admin/LIMIbackend` | `limi-backend.service` | 8000 |
| ❌ **Capybara Game** | `/opt/capybara-game` | PM2 `limi-kid` | 18001 |

**关键事实**：登录账号是 `admin`，而 LIMI 的目录就在 `/home/admin/` 下面 ——
也就是说 `admin` **对 LIMI 是有权限的**。所以不要靠"我保证不碰"，
而是**把命令写死**：不列 LIMI 路径、不开 LIMI 的库、不显示 LIMI 的进程。

### 3.2 溪语服务以系统用户 `xiyu` 运行

读生产数据库需要切身份：

```bash
sudo -n -u xiyu sqlite3 -readonly /opt/xiyu-ai/data/bot.db "SELECT ..."
```

**所有 `sudo` 都要带 `-n`**（non-interactive）。不带 `-n` 时，一旦 sudo 需要
密码，命令会**永久挂住**，在自动化里表现为超时而不是报错，很难排查。

### 3.3 不允许的操作

- ❌ 修改 / 删除 / 移动服务器上任何文件
- ❌ `systemctl start|stop|restart|enable|disable`
- ❌ 向任何表执行 `INSERT` / `UPDATE` / `DELETE` / `DROP`
- ❌ 触发任何真实外发消息（不得为验证主动发消息给用户）
- ❌ 读取或输出 `.env` 的**值**（只允许列键名）
- ❌ 密码登录；不得索取、输入或转述任何密码
- ✅ 允许：`systemctl is-active` / `show`、`ls`、`stat`、`sha256sum`、
  `df`、`free`、`uptime`、`journalctl`、`sqlite3 -readonly` 的 `SELECT`

## 4. 四个已经踩过的坑（照抄结论，别重复踩）

### 坑 1：`Permission denied (publickey,password)` 不代表公钥没装

**症状**：报 `Permission denied (publickey,password)`，看起来像公钥缺失或权限错。

**真相**：这个报错**极具误导性**。旧密钥 `xiyu-readonly` 是**带 passphrase 加密**的。
配合 `BatchMode=yes` 时，OpenSSH 无法询问口令，于是**在签名环节静默放弃**：

```
debug1: Offering public key: ... xiyu-readonly ...
debug1: Server accepts key: ... xiyu-readonly ...          <-- 服务器已经认可这把公钥
debug3: sign_and_send_pubkey: signing using ssh-ed25519 ...
debug2: we did not send a packet, disable method           <-- 客户端放弃发送签名
admin@39.106.153.59: Permission denied (publickey,password).
```

**判据**：出现 `Server accepts key` 就说明**公钥是好的**，故障在客户端本地。

**如何判断一把私钥是否带 passphrase**（不要用"搜 `bcrypt` 字样"，
私钥是 base64 编码，KDF 名不以明文出现）：

```bash
# 头部前缀判定：未加密密钥固定以 b3BlbnNzaC1rZXktdjEAAAAABG5vbmU 开头
head -2 ~/.ssh/<私钥> | tail -1 | cut -c1-44
#   b3BlbnNzaC1rZXktdjEAAAAABG5vbmU... -> cipher=none，未加密，可直接自动化
#   含 YWVzMjU2 / YmNyeXB0                -> aes256-ctr + bcrypt，已加密

# 或者：秒回=未加密；卡住不动=正在等 passphrase
ssh-keygen -y -f ~/.ssh/<私钥>
```

**结论**：自动化只用 `xiyu-readonly-nopass`。`xiyu-readonly` 已废置，别再试。

### 坑 2：PowerShell 管道跑脚本会导致 `exit 127`

**症状**：脚本明明执行完了，退出码却是 `127`，末尾报
`bash: line NNN: $'\r': command not found`。

**原因**：PowerShell 向原生程序管道传输时，会在**末尾**附加一个 `\r`。

**正确做法**：用 base64 走 stdin。

```powershell
$b64 = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes(
         (Get-Content -Raw .\xiyu-p0.sh) -replace "`r`n","`n"))
$b64 | ssh -i "$env:USERPROFILE\.ssh\xiyu-readonly-nopass" `
       -o BatchMode=yes -o IdentitiesOnly=yes `
       admin@39.106.153.59 'base64 -d | bash'
```

在 bash 里则可以直接用重定向（前提是脚本是 LF 行尾）：

```bash
ssh -i ~/.ssh/xiyu-readonly-nopass -o BatchMode=yes admin@39.106.153.59 \
    'bash -s' < xiyu-p0.sh
```

### 坑 3：`admin` 读不到 `xiyu` 属主进程的 cwd

**症状**：进程/分区隔离检查看起来"通过了"，但**溪语主进程根本没出现在列表里**。

**原因**：`readlink /proc/<pid>/cwd` 对别的用户属主的进程会失败并返回空，
于是 `case` 匹配落空，进程被**静默漏掉**。

```bash
# 错误写法：会漏掉 xiyu-ai 主进程
readlink /proc/$pid/cwd

# 正确写法
sudo -n readlink /proc/$pid/cwd
```

**同理**：`journalctl -u xiyu-ai` 不加 sudo 只会打印一行 `No entries`。

### 坑 4：数据库时间戳与系统时间差 8 小时

服务日志同时打印 UTC（`2026-09-14T14:26:40Z`）和 CST（`22:26`），
而数据库 `updated_at` **疑似按 UTC 落库**。解读投递时间线前必须先确认口径，
否则会把 22 小时误读成 6 小时。

另外 `agency_feedback` **没有 `next_state` 列**，真实列为：
`id, account_id, companion_id, intention_id, action_id, source_message_id,
kind, raw_ref, interpretation, confidence, created_at`。

## 6. 换到新机器时的配置（一次性）

**第 1 步：在**新机器**上生成一把免密专用密钥**

```bash
ssh-keygen -t ed25519 -N "" -C "xiyu-readonly-nopass-<你的机器名>" \
    -f ~/.ssh/xiyu-readonly-nopass
```

⚠️ `-N ""`（空 passphrase）**必须真正传成空串**。PowerShell 直接调用时
空字符串参数可能被丢掉，从而转成"索要口令"并卡死；用 bash 或 batch 包装更稳。

**第 2 步：把新公钥打印出来**

```bash
cat ~/.ssh/xiyu-readonly-nopass.pub
```

**第 3 步：请用户用 `admin` 登录服务器，粘贴下面这段**
（把 `<新公钥内容>` 换成上一步的输出）

```bash
mkdir -p /home/admin/.ssh
chmod 700 /home/admin/.ssh
echo '<新公钥内容>' >> /home/admin/.ssh/authorized_keys
chmod 600 /home/admin/.ssh/authorized_keys
```

要点：四行都要跑、`chmod` 不能省（sshd 对权限很严格）、
用 `>>` 追加不会冲掉已有公钥。

**第 4 步：按第 5 节验证。** 看到 `MARKER:LOGIN_OK` 即成功。
