## 先看这里：项目现在解决什么问题

这是一个面向 VR 大空间运营者的“事实录入 → 周报复盘 → 经验沉淀 → 经营动作”工作台。它不是单纯的数据看板，也不是把运营回答原样拼成周报，而是把一周的经营事实整理成可追溯、可解释、可复制的管理材料。

当前已经落地的核心能力：

- 按周、按门店录入经营数据，保留完整业务日期和历史修订。
- 从来源表预览各渠道全部商品的销售票数和销售额，运营人员确认后才写入草稿；次卡仍使用独立字段，不从渠道数据反推。
- 写入飞书前做查重、字段映射和差异预览；写入后可再次对比本地与飞书。
- 周报按“现象 → 因果调查 → 复盘判断 → 经验/动作 → 完整周报”推进。
- AI 只负责需要判断和语言组织的部分；数字、日期、口径和同步状态由程序掌控。
- 最终周报使用执笔人的经营口吻，不展示调查轮次，不复制“运营说了什么”。

## 外部信息检索与证据边界（本地优化阶段）

外部信息分两类处理：项目档案中的门店地址、场域、自然客流和本地生态属于一次性/低频背景；竞品活动、节假日、天气、行业案例和打法证据属于按需动态检索。两类资料都必须保留来源链接、抓取时间、适用门店和状态，不能悄悄写成本周经营事实。

- 在“项目档案 → 外部背景资料”中可重新搜索或手动添加来源。搜索结果先进入“待应用”，运营确认后才成为“已应用”版本；重新搜索不会覆盖旧版本。
- “经营地图”和“打法方案与验证”提供按需外部证据检索。勾选资料并应用后，资料会随下一次 AI 分析作为背景证据传入，并明确标注为外部参考，不证明本店因果。
- 所有资料按项目/门店隔离，东坝与中影不会混用；动态搜索结果不会自动进入项目档案。
- 后端提供统一 `/api/strategy/external-search` 适配层。当前未配置正式搜索服务时默认走“手动来源”兜底，避免免费服务器因为公共搜索网络波动卡住；配置 `EXTERNAL_SEARCH_API_ENDPOINT` 与 `EXTERNAL_SEARCH_API_KEY` 后即可切换正式搜索供应商，密钥不暴露到浏览器。
- 当前行业知识绑定已校正：东坝对应“商场或影院自然客流型门店”，中影对应“科技馆或文旅场馆依附型门店”。

### 当前阶段的三个重要约束

1. 经营事实、经验和下一步动作是不同类型的信息，不能互相冒充。
2. “调查停止”不等于“因果未确认”；主要机制成立但未解释全部幅度时，结论会标记为“主要解释已成立”。
3. “待补证事项”不是经营动作。它会放在复盘区域的折叠信息中，不会生成空的下一步动作卡片。

## 产品概览

这是元趣世界 VR 大空间经营策略工作台。经营地图是默认首页；运营填数、飞书同步与周报复盘作为同一产品的子功能，共用经营事实、分析结论和经验来源。

首页不保存第二份经营数字：节点指标、变化和健康状态直接由周记录计算，周度信号和已确认经验引用现有周报对象；只有长期机会、打法状态和执行验证记录保存在独立的长期策略状态中。

运营录数仍把“人填数”和“飞书写入”拆成两个阶段：

1. 运营人员在页面中按周、按门店录入并保存草稿。
2. 页面进行必填校验、异常提示和同步前差异预览。
3. 人工确认后按总设置选择：只生成本地 outbox，或调用同步服务通过飞书 Open API 写入正式事实表。
4. “周报生成”按周期合并门店数据，生成可编辑、可复制的周报草稿。

“周报生成”页采用单一成果链路：`确认数据与经营事实 → 识别问题与机会 → 在对应卡片内补充因果 → 生成复盘分析 → 选择/补充经验 → 选择/补充下一步动作 → 生成并复制完整周报`。页面本地存储只承担草稿和防丢作用，正式留存内容以复制出去的完整周报为准。

周报正文采用结论结构：核心数据固定保留，门店、渠道、次卡、播控和长期趋势只有在达到重要性阈值时才进入调查；最终正文只展示有证据边界的问题/机会结论，不展示调查问题。这里的“渠道”固定指各渠道售出的全部商品，“次卡”只指独立次卡字段中的次卡商品，二者不会互相替代。完整数据和口径统一收进可展开附录。

## 使用

### 今日经营（日常协同层）

“今日经营”是周报之外的日常入口：它每天只先给一个值得看的经营变化，再给一组可选择的经营想法。它不会自动改写周数据，也不会把想法直接当成正式打法。

- `GET /api/today?date=YYYY-MM-DD&venue=all|东坝|中影`：读取指定日期和门店范围的简报、经营想法、可用上下文和“我的想法”。
- `POST /api/today/refresh`：重新读取当天来源表快照，并按总设置调用外部模型；模型不可用时使用同一上下文契约的本地兜底，不会阻塞页面。
- `POST /api/ideas/refresh`：只刷新经营想法，不改变周记录和周报。
- `POST /api/ideas/:id/reaction`：记录“先留着 / 不适合”和简报反馈；保存或正在深入的想法会跨日期保留。
- `POST /api/ideas/:id/deepen`：为选中的想法补充待确认条件、潜在收益和最小探索步骤。
- `POST /api/ideas/:id/convert`：把想法标记为打法候选，后续仍需在“打法方案”中完成正式目标、指标和验证设计。

日常层的服务端运行状态分别保存在 `data/runtime-state/daily.json`、`ideas.json` 和 `interactions.json`。上下文由程序组装：本店周记录、当天来源快照、项目/门店档案、待处理问题、进行中的验证和可调用经验；模型只负责判断和组织表达。`backend/daily-operating-prompts-v2.json`、`daily-operating-schema-v2.json` 和 `data/idea-lenses-v1.json` 是可替换的版本化契约，不把某一周的答案写死在页面中。灵感输出采用“自然开场 → 具体主意 → 可以怎么玩 → 为什么想到它 → 最小探索”的交流结构，同时继续区分事实、推断和脑洞。

直接打开 `index.html` 仍可做离线录入；要启用总设置的服务端持久化和模型代理，请启动 `node backend/feishu-sync-server.mjs` 后访问 `http://127.0.0.1:4174/`。

### 溪语经营知识联动（本地第一期）

工作台与仓库根目录的溪语服务通过窄知识桥联动：溪语的微信入口和网页 playground 共用同一条桥，先判断对话是否涉及工作，再按项目/门店范围读取有限的经营上下文；回复完成后，新增业务信息只进入“溪语采集”候选箱，不能直接改写事实、机会、验证或正式经验。纯私人聊天不会读取或回流企业内容，混合聊天只保留工作片段。

- `GET /api/knowledge/catalog`：返回当前项目、门店、经营节点和允许的资产类型目录。
- `POST /api/knowledge/retrieve`：按项目、门店、主题和资产类型返回程序过滤后的上下文包；只有已发布且 `retrievalEligible=true` 的经验可作为正式经验召回。
- `GET/POST/PUT /api/intelligence/candidates`：候选信息的读取、幂等写入和人工状态处理；“已确认候选”仍需在对应模块应用，不等于正式资产。
- 页面中的“溪语采集”是候选箱入口，可按状态筛选、确认保留、标记待补充或暂不采用。候选不会自动发布经验。
- 溪语侧提示词位于仓库根目录 `../config/prompts/work-context-router-v1.json` 与 `work-intelligence-extractor-v1.json`；候选回流使用本地 outbox 并带幂等键，工作台短暂不可用时不会阻塞主聊天。
- 本地启用只需在溪语 `.env` 设置 `XIYU_WORKBENCH_CONTEXT_URL=http://127.0.0.1:4174`；正式环境应改为服务端地址并配置服务令牌，不能把令牌放到浏览器。

两边都保留“程序管状态、模型做理解”的边界：模型不决定权限、事实成立、因果确认或经验发布。溪语联动烟测可用 `node scripts/enterprise_context_smoke.mjs`，全量 ESM 导入烟测可用 `node scripts/import_smoke.mjs`（Windows 和 CI 均支持）。

周记录、草稿和周报修订仍默认保存在浏览器 `localStorage`；“总设置”已改为优先保存到当前同步服务，浏览器只保留非敏感缓存：

- `yuanqu_weekly_ops_records_v1`：周记录、草稿、同步状态
- `yuanqu_weekly_ops_settings_v1`：周定义和录入设置的本地缓存（不保存 API Key）
- `yuanqu_weekly_ops_outbox_v1`：待接入飞书的同步任务
- `yuanqu_weekly_ops_reports_v1`：经营背景、周报草稿和修订记录
- `yuanqu_operating_strategy_workbench_v1`：长期机会、打法状态、方案版本和验证结果；不复制经营数字

本轮本地兼容优化另外将上述工作台状态通过本机服务保存到 `data/runtime-state/workbench.json`，浏览器缓存仍保留作为离线兜底。线上要实现跨设备持久化，仍需单独接入 EdgeOne Blob。

总设置通过 `GET/PUT /api/settings` 读写服务端配置。API Key 只保存在服务端，页面仅显示“已保存”状态；切换本地/外部模型、刷新页面或更换同一服务下的浏览器不会清空配置。服务不可用时页面回退到本地缓存，但不会把缓存中的 Key 回写或展示。

## 经营策略与打法闭环

经营地图采用四步选择链路：`本周期经营状态 → 专家问题/机会 → 解决方向 → 可执行打法`。第一步明确展示周期起止日期、门店范围、指标粒度和计算公式，并同时给出上一可比周期、近 4 周历史基线和最多 8 周趋势。程序计算出的涨跌、结构集中或数据缺口只属于“候选信号”，不会直接显示成专家结论。

原因调查与干预探索并行：经营原因尚未确认时，页面仍可展示与目标指标直接绑定的低可信解决方向和小规模测试打法，并清楚标注其假设边界。只有指标无法计算、指标口径不清，或打法无法绑定任何可观测指标时，后续方案才会被阻断。

用户点击“运行专家分析”后，页面把候选信号与不可改写的证据表、项目档案、历史经营事实、经营日历、门店画像、已确认经验、验证记录和行业口径一起提交到服务端 `POST /api/strategy/analyze-node`。服务端使用版本化的 `operating-node-analysis-v5` 提示词调用已配置模型，校验每条结论的证据引用、可信度、比较基础和缺失事实；第一次不合格时允许自动修复一次。只有通过协议且 `include=true` 的专家信号才进入第二步。相同事实指纹、提示词版本、知识库版本和项目档案版本可复用缓存。专家分析完成后，还会使用独立提示词审查长期机会，但不会把未经确认的假设自动写成经营事实。

行业比较默认不展示一个模型猜测的“行业平均值”。只有知识库提供了来源可追溯、指标定义和场景均可比的 benchmark 时，模型才可使用行业基准；否则页面明确显示“暂无可信同口径行业基准”，并以本店历史和相同经营日历阶段为主。

选择打法后进入独立的“打法方案”页。一个打法不是零散动作列表，而是一条围绕同一量化目标的完整路径。例如门口体感互动应完整覆盖“吸引驻足 → 参与互动 → 获得进店理由 → 店内承接 → 核销/成交”，并逐段绑定可记录指标。

该页通过 `tactic-plan-design-v3` 提示词先生成目标指标、公式、当前基线、目标值、目标周期和目标理由，再生成目标客群、执行场景、作用机制、完整路径、资源条件、过程指标、结果指标、保护指标、测试周期、比较方式、成功标准、停止条件和记录方法。推荐目标不得脱离当前需要改善的节点。涉及技术实现时只生成技术要求与 GitHub 检索词，不把搜索结果冒充已验证案例。

周报复盘使用 `weekly-review-v6.3` 提示词注册表，依次执行“信号与因果假设、运营回答证据审查、复盘结论、经验候选、下一步动作候选”。每一步都有独立业务职责和 JSON 输出契约；项目档案、经营日历、历史周报结论、经验、验证记录和长期机会作为共享上下文按需进入，不允许模型把背景信息改写成已证实因果。

```text
周经营事实 / 周报信号
        ↓
程序候选信号
        ↓ 版本化提示词 + 严格输出校验
专家确认的问题或机会
        ↓
经营日历 + 门店画像 + 内部经验 + 行业打法
        ↓ 检索与规则过滤
解决方向与可选打法
        ↓ AI适配、排序，运营确认
打法方案与验证设计
        ↓ 执行结果
已验证经验 / 无效打法 / 适用边界
```

方案本身不是经验。只有执行结果完成验证、运营确认适用边界后，才能沉淀到内部经验库并参与后续推荐。经营日历只作为阶段背景，不能单独证明本周数据变化的因果。

### 项目基础档案

“项目档案”页保存不需要每周重复填写的长期背景，包括项目/产品、国家城市、核心客群、购买决策者、自然客流来源、经营漏斗、IP/内容资产和共性限制；门店档案补充各门店的场域类型、客群、客流来源、空间设备、人员条件和执行限制。

档案由后端 `GET/PUT /api/strategy/profile` 持久化到 `data/strategy-project-profile.json`，专家节点分析与打法方案生成都会读取。档案属于分析背景，不会被写成本周经营事实；档案更新后旧分析会自动过期。

## 周报复盘 v6

当前周报不再把“重点问题”或调查记录直接复制进最终成稿。程序先计算单周变化和最多八周趋势，再按每条信号检索相关历史结论与已确认经验；每张卡片先展示目标指标和待验证假设，再以不显示轮次的对话方式补充经营事实。回答无关时会解释影响环节不匹配，最多追问两次，重复或没有信息增量时停止。

### 一张复盘卡片最终写什么

最终卡片只保留三层，顺序固定：

1. **经营现象**：程序计算的事实和比较基线，只出现一次。
2. **复盘判断**：周报执笔人基于事实、历史和经营背景形成的直接判断，先给结论，再解释影响机制。
3. **判断边界**：说明哪些已经可以判断，哪些幅度、替代因素或长期规律仍未被证明。

正文禁止出现“运营说明、运营回答、根据对话、数据显示、模型判断”等过程性措辞，也不引用运营原话。运营回答仍会完整保存在卡片调查记录中，用于追溯，但不会作为周报正文直接展示。

### 因果结论的四级状态

| 层级 | 周报含义 | 卡片状态 |
| --- | --- | --- |
| `confirmed` | 原因和主要变动幅度都有直接证据 | 已形成结论 |
| `primary_supported` | 主要影响机制和变化方向成立，但尚未解释全部幅度 | 已形成结论·中等置信度 |
| `related_only` | 信息与指标有关联，但不足以支持主要原因 | 待观察 |
| `unconfirmed` | 尚无有效因果证据 | 待观察 |

调查停止、达到追问上限或重新开始调查，只描述对话状态，不会覆盖上述因果层级。旧卡片刷新时会自动迁移到当前的执笔格式；如果旧结论包含过程性复述，系统会重新生成简洁的经营判断。

### 经验与下一步动作

生成复盘分析后，AI 才会生成候选经验和候选动作。二者都不是自动写死的结论，运营可以修改、删除和选择保留。

- **经验沉淀**：必须同时有背景、实际动作、可观察结果和适用边界；没有结果或因果未确认时可以为空。
- **待补证事项**：只表示还需要补什么证据，放在复盘区域的折叠信息中，不进入下一步动作。
- **下一步动作**：只保留会改变经营结果的 `intervention`，必须有目标、依据、范围、时间窗口、责任角色、步骤、指标、基线、完成标准和停止条件。没有满足条件的动作时，页面明确显示“本周没有满足执行条件的 AI 经营动作”。

最后点击“生成完整周报”才会固定本次选择，形成可复制版本。完整周报展示经营结论、选中的经验和选中的经营动作，不展示内部调查轮次和无效候选。

本地内测模式与外部模型使用相同的五段流程和 JSON 契约；内测结果由提示词模拟器产生，不把某一周的结论硬编码进页面。接入外部模型后使用 v6 提示词 ID 与契约。相同周期和数据指纹再次刷新时复用原卡片，不重新创建或重复提问；点击“重新开始调查”会保留旧调查并新建独立尝试。

## 重要边界

- 播控已经按“周 × 门店 × 项目”进入标准事实结构；正文展示播控概览，完整项目明细保留在附录。
- 运营答复是因果审校证据，不会原样复制进最终周报。回答不相关或证据不足时最多追问两轮，之后标记为待观察；完整对话和历史调查仍保留在本周记录中。
- 最终周报不包含调查问题；无法闭环的事项以“已确认的变化 + 无法归因的边界 + 待观察状态”形成结论。

## 门店拆分周报包（本次调整）

同一周期不再只有一份把多家门店混在一起的分析对象，而是一个“周期周报包”：包内为每家门店各自保存一份独立周报。门店周报拥有自己的数据输入、上期对比、经营事实、问题与机会调查、对话记录、复盘结论、经验候选、下一步动作和修订历史；任何一家门店的回答不会进入另一家门店的 AI 上下文。

- 周期公共信息（项目名称、周定义、通用日历）放在周报包级别。
- 门店画像、门店经营事实和门店数据放在门店周报级别。
- “周报生成”会按当前周期的每家门店分别生成；页面用门店切换卡查看和处理，不再把两家店的结论混成一张卡。
- 旧版合并周报不会被删除，作为“旧合并记录”只读保留；重新生成后才形成新的门店独立版本。
- 复制完整周报时只复制当前选中门店的正式成稿，避免把多家门店内容误粘到一个门店的汇报里。

存储上仍兼容旧的 `yuanqu_weekly_ops_reports_v1`：新增 `reportPackage.schemaVersion = weekly-report-package-v1`，以 `periodId + venue` 作为门店周报键。历史数据首次打开时只做非破坏性包初始化，旧合并分析保存在 `legacyCombinedAnalysis`，不会覆盖原记录。
- 运营只补充事实、实际动作和结果证据；可复用经验由规则或模型先生成候选，再由运营确认。证据不足时明确显示“本周未形成可复用经验”。
- 数值字段使用 `input[type=number]`，保存前会转为 JavaScript number。
- 周开始、周结束和每天的日期都按真实 `YYYY-MM-DD` 保存；周一到周日只作为辅助显示，不参与日期计算。
- “新建周记录”按 `周期ID + 门店` 幂等：已有记录会直接打开，不会重复创建。
- “确认并生成同步任务”不会伪装成已写入飞书；选择同步服务模式后，只有飞书 Open API 成功返回才标记“已写入飞书”，失败会保留任务和错误原因。
- 已同步记录不直接覆盖原值，后续调整应通过“新修订”形成追溯链。

## 已核验样例数据

2026-08-08 至 2026-08-21 的东坝、中影样例已按飞书 `【周报复盘】辅助表格` 修订号 `9753` 重新核验。页面会自动识别并替换早期错误样例：播控数据不再充当日客流、占位日票房已换为来源表真实日票房、渠道“销售票数”按来源表每日票数字段汇总、次卡销售金额与核销次数分开。由旧错误数据生成的本地同步任务会标记作废，旧周报保留在历史修订中并要求重新生成。

运营人员浏览器
  ├─ 录入、校验、草稿、周报修订：localStorage
  ├─ 总设置：GET/PUT /api/settings（服务端持久化，API Key 不回传）
       └─ 确认写入

  ├─ 从 backend/.env 读取飞书应用凭证
  ├─ 获取 tenant_access_token
  ├─ 按 data/feishu-target.json 的字段映射读表、查重、upsert
  └─ 只写入录入_*事实表，不写 AI周报结论
       ↓
飞书表：周报复盘辅助表_简化录入版_v3

周报模型分析通过 `POST /api/weekly-report` 代理；经营节点专家分析通过专用的 `POST /api/strategy/analyze-node` 运行事实包、版本化提示词和输出校验。浏览器不直连模型，也不接触 API Key。最终使用者不需要安装 CLI，也不需要知道 App Secret 或模型 Key；密钥只存在运行同步后端的服务器上。

## 快速启动

### 本地运行

要求 Node.js 18 或更高版本（服务使用原生 `fetch`）。在项目根目录执行：

```powershell
cd workbench
node backend/feishu-sync-server.mjs
```

然后打开 <http://127.0.0.1:4174>。确认后端状态：

```powershell
Invoke-RestMethod http://127.0.0.1:4174/health | ConvertTo-Json
```

正常结果应包含 `provider: "feishu-open-api"`、`configured: true` 和目标表版本号。

### 线上运行

线上必须同时部署静态页面和 Node 后端，并把域名的 `/api/feishu/*` 反向代理到后端端口。服务器环境变量或服务器本地 `backend/.env` 中配置飞书凭证；不要把 `.env`、App Secret 或目标表管理权限放进前端构建产物。

公网页面会使用同源地址 `/api/feishu/sync`，不会把请求发到访问者自己的 `127.0.0.1`。生产环境还应在反向代理层增加 HTTPS、登录鉴权、请求限流，并把 CORS 从开发用的 `*` 收窄到实际域名。

## 后端配置

配置文件为 `backend/.env`，已加入 `.gitignore`：

```dotenv
FEISHU_APP_ID=你的飞书应用 App ID
FEISHU_APP_SECRET=你的飞书应用 App Secret
FEISHU_SPREADSHEET_TOKEN=目标电子表格 token
FEISHU_SOURCE_SPREADSHEET_TOKEN=渠道日销售来源表 token
FEISHU_API_BASE=https://open.feishu.cn/open-apis
WEEKLY_OPS_PORT=4174
WEEKLY_OPS_HOST=127.0.0.1
```

飞书应用需要开通电子表格读写权限，并且目标表对该应用可编辑。应用凭证只用于服务端换取租户访问令牌；每次写入前由后端完成令牌缓存和 API 调用。

运营填数页的“读取本周来源数据”调用 `POST /api/feishu/source-preview`。后端按门店读取来源表的 5 个渠道页签，按真实业务日期汇总每日销售票数和销售额并返回预览；累计列不参与求和。普通渠道票数读取每日 `今日票数`；小程序分别读取 `今日非线下销售数` 和 `今日线下销售数`，与对应销售额一起拆到“小程序其他”和“线下”。页面只在用户点击“应用所选到当前草稿”后写入草稿，来源表 token 和应用凭证均不暴露给浏览器。

来源表到业务字段采用固定口径：`开店宝 → 大众`、`小程序·非线下 → 小程序其他`、`小程序·线下 → 线下`。渠道区的销售票数和销售额都表示该渠道售出的全部商品，不表示“该渠道售出的次卡”；次卡销售、权益与核销只读取独立 `cards` 数据。业务所称“分销”默认与小程序线下同源，不得和“线下”重复相加；正式飞书 `录入_渠道` 会按统一名称写入线上渠道和“线下”渠道，若页面只填写“分销”则同步时归一为“线下”。`录入_周经营.线下销售额` 同时保留门店周汇总，两者属于不同粒度，不在分析中重复相加。原始来源名仍保留在追溯数据中，周报与 AI 输入同时携带这套口径说明。

## 数据落盘规则

所有数据先在页面形成结构化记录，再由后端按“事实表主键”幂等写入。相同主键再次确认会更新对应行，不会无条件追加重复行。

| 页面数据 | 飞书事实表 | 粒度 / 主键 | 日期权威 |
| --- | --- | --- | --- |
| 周经营 | `录入_周经营` | 周期 × 门店 / `周期ID + 门店ID` | `周开始 + 周结束` |
| 渠道销售（全部商品） | `录入_渠道` | 周期 × 门店 × 渠道 | 周期字段 |
| 日客流 | `录入_客流` | 业务日期 × 门店 | `业务日期` |
| 日票房 | `录入_票房` | 业务日期 × 门店 | `业务日期` |
| 次卡统计（仅次卡商品） | `录入_次卡` | 周期 × 门店 × 卡种 | 周期字段 |
| 次卡累计 | `录入_次卡累计快照` | 快照日期 × 门店 | `快照日期` |
| 播控 | `录入_播控` | 周期 × 门店 × 项目 | 周期字段 |

周一、周二等日期标签仅作为展示辅助；实际匹配使用完整 `YYYY-MM-DD`。周经营、渠道和次卡是周粒度，不应人为拆成 7 天；客流和票房是日粒度，必须带真实业务日期。

字段的完整定义、类型、来源和限制以 `data/field-mapping.json`、`backend/schema.json` 和 `docs/field-mapping.md` 为准。若页面字段和飞书列名不一致，只修改映射文件和后端转换，不要在页面中散落硬编码。

## 页面使用流程

1. 在“总设置”确定周起始日、自然日数、时区和周期 ID 连接符。
2. 点击“新建周记录”，选择周期和门店。`周期ID + 门店` 已存在时直接打开原记录，不重复创建。
3. 录入周经营、7 天日明细、渠道、次卡和播控。渠道区填写各渠道全部商品的销售票数/销售额；次卡区只填写次卡商品的销售、权益和核销。数值字段保存为数字，空值保存为 `null`。
4. 点击“保存草稿”只写浏览器本地，不会访问飞书。
5. 点击“校验”检查必填项、日期范围、异常值和重复主键；校验不会修改数据。
6. 点击“确认并生成同步任务”，再在确认弹窗中确认。新安装页面默认调用同步服务；也可切换为仅生成本地 outbox。
7. 后端成功返回后，页面才标记“已写入飞书”；失败会保留任务、错误原因和原始记录，便于重试。

如果记录已经存在“待同步”或“同步失败”任务，页面会显示“执行同步”或“重试同步”，继续使用原任务，不会重复创建。若当前同步方式仍是本地 outbox，点击后会直接引导到“总设置”切换为同步服务；如果本地数据已经发生变化，旧任务会先作废，再允许生成新任务。

记录状态与同步状态是两套信息：`draft / confirmed / deleted` 描述记录生命周期，`local / queued / syncing / success / failed` 描述同步进度。已确认记录的后续修改生成新的修订号，保留历史版本。

## 同步接口

### `GET /health`

返回服务、Provider、凭证是否配置和目标表版本。该接口不返回 App Secret 或访问令牌。

### `POST /api/feishu/sync`

请求体是页面生成的 outbox 任务，至少包含 `taskId` 和 `payload`。`payload.schema_version` 当前为 `feishu-sink-v1`，包含 `weekly_core`、`daily_metric`、`channel_metric`、`card_metric`、`playback_metric` 等结构化段。

联调时可以加入 `dryRun: true`：后端会读取表头、查找匹配行并返回预计写入行号，但不会调用写入接口。例如：

```powershell
$task = @{ taskId = 'dry-run-001'; dryRun = $true; payload = $payload } | ConvertTo-Json -Depth 20
Invoke-RestMethod http://127.0.0.1:4174/api/feishu/sync -Method Post `
  -ContentType 'application/json' -Body $task | ConvertTo-Json -Depth 20
```

正式成功响应会返回 `written`、`warnings` 和目标表信息。`warnings` 是口径提示，不代表写入失败；例如当前平台加售结算额与扣佣结算预估的对应关系仍需运营确认。

### `POST /api/feishu/compare`

“对比飞书”按钮调用此只读接口。它按同步任务的相同字段映射读取飞书对应行，返回逐行、逐字段的 `local` 与 `feishu` 值，并给出 `same / different / missing` 状态和汇总计数。该接口不会写入飞书。

### `GET /api/feishu/sources`

返回可公开展示的飞书落盘目录，包括工作簿名称、页签名称、数据粒度和可点击链接。经营地图的“数据来源与追溯”模块从该接口读取正式落盘位置；应用凭证、密钥和其他后端配置不会返回前端。

页面上的两个标签含义不同：同步标签表示最近一次写入请求的结果；一致性标签表示最近一次对比结果。常见一致性标签包括“未核对飞书”“数据已同步”“数据有差异”“飞书缺少对应行”和“本地已修改，待对比”。本地数据在成功同步后再次修改，会自动变成“本地已修改，待对比”，避免把旧的同步成功误认为当前仍一致。

## 周报与 AI 分析流程

周报页不是把所有数字平铺出来，而是按以下状态推进：

```text
确认事实 → 识别重要变化 → 生成初始假设 → 卡片内补充经营事实
       → 复盘结论 → 选择/补充经验 → 选择/补充下一步动作 → 生成完整周报
```

- 程序负责数字计算、环比、趋势、缺失检查、证据引用和状态机。
- 模型负责经营信号措辞、因果假设、有限轮次追问、复盘结论、经验候选和动作候选。
- 运营回答保留在对应卡片的调查记录中；最终完整周报只展示结论，不展示内部轮次和未闭环问题。
- 本地内测 Provider 使用和外部模型相同的提示词结构，但由提示词模拟器返回结果，不把某一周的结论写死。
- 提示词与输出契约位于 `backend/weekly-review-prompts-v6.json`、`docs/weekly-review-v6-design.md` 和 `backend/report-schema.json`。

外部模型必须返回合法 JSON。程序计算出的 `totals`、渠道、次卡、趋势、播控和数据完整性结果是权威值，模型不能改写；其中渠道分析固定使用“全部商品按渠道”的销售票数/销售额，次卡分析只使用独立 `cards` 数据，模型不得用渠道数据反推次卡销售。无法证明的因果只能标记为待观察或继续调查。

## 常见问题排查

| 现象 | 优先检查 |
| --- | --- |
| 页面提示无法连接同步服务 | 后端是否启动、端口是否为 4174、浏览器是否使用了正确的同源 API 地址 |
| `/health` 显示 `configured: false` | `backend/.env` 是否存在，变量名是否完全正确 |
| 飞书 API 返回 401/权限错误 | App ID/App Secret 是否匹配，应用是否有电子表格读写权限，目标表是否授权给应用 |
| 任务显示失败但表里没有新增 | 这是预期的失败保护；查看任务中的 `syncError`，修复后重试，不要手工改成 success |
| 同一周出现重复记录 | 检查 `周期ID + 门店ID` 是否一致；不要改变主键后再重复提交 |
| 日客流/次卡出现口径提示 | 这是当前已知的语义边界，见 `docs/field-mapping.md`，不能由程序擅自猜测 |
| 模型接口返回 HTTP 501 或非 JSON | 检查模型 Provider、API 地址、模型名称和服务端是否实现了约定的 JSON 响应 |

## 变更与验收清单

涉及字段时按以下顺序修改：

1. 更新 `data/field-mapping.json` 和 `backend/schema.json`。
2. 更新 `data/feishu-target.json` 的目标 sheet、列名、粒度和主键。
3. 更新后端 `makeRows` 的转换与口径警告。
4. 更新页面字段、校验规则和字段映射说明。
5. 若影响 AI 分析，更新提示词 JSON、`report-schema.json` 和对应设计文档。
6. 运行 `node --check backend/feishu-sync-server.mjs`，并用 `new Function` 检查 `index.html` 脚本。
7. 先调用 `/health` 和 `dryRun: true`，确认目标行、警告和飞书 revision；最后才允许真实写入。

# 经营闭环补强（2026-08-31）

本版本补齐了“打法与验证”从一次性方案到持续经营资产的基础链路：

- “打法方案”页面现在先展示全部已选打法，固定后的方案不再依赖经营地图当前选中项才能找回。
