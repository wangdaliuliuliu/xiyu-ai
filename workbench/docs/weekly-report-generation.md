# 周报生成逻辑

## 页面定位

“周报生成”是当前运营填数台中的独立页面。它以一个周期为单位，合并该周期的门店记录，寻找各门店最近一期历史记录，再生成可编辑、可复制的成品周报。

## 固定流程

1. 运营完成周期内各门店数据录入。
2. 程序构造结构化 report input，计算汇总值、可比环比、贡献结构和最多八周趋势。
3. 程序筛选重要变化与连续趋势，为每条信号建立不可改写的证据包。
4. 检索层按信号召回相关历史结论和已确认经验；召回内容只能用于提出假设，不能证明本周因果。
5. Provider 判断经营事实的相关性。证据不足时进入右侧因果调查，最多追问两轮。
6. Provider 返回 `reviewConclusions`；问题只保存在 `investigations`，不会进入最终周报。
7. 人工可以修改结论表达；修改不会回写经营数字。
8. “复制完整周报”同时提供富文本和纯文本。

## Provider 边界

- local：只生成事实、趋势、检索结果和证据缺口，不伪装成模型生成因果结论。
- api：页面直接调用兼容 OpenAI Chat Completions 的模型接口；地址、Key 和模型名由使用者在总设置中配置。
- 模型配置通过同步服务的 `/api/settings` 保存到服务端，API Key 不回传浏览器，也不写入飞书；页面只显示是否已配置。模型请求统一经 `/api/weekly-report` 由服务端代理。
- API 不得直接返回 HTML；这样展示格式、复制格式和数据口径仍由本项目控制。

## 分析边界

- 本期和上期均存在的门店才进入整体环比。
- 数字事实、历史趋势、经营事实、检索经验、调查问题和最终结论分层保存。
- 没有足够证据时不推断因果；最终周报写清“无法归因”的边界，而不是保留问题。
- 元周报已有数据不得静默删除；无法取得时进入“数据口径与完整性”。
- 播控按项目进入结构化事实表，正文保留简要经营概览，完整项目明细进入附录。
- 当前“核销/使用”只指次卡，不代表全量票务核销。
- 调查问题不设固定数量；每条问题都有期望回答范围、相关性审校和最多两轮追问。
- 经营复盘按“场景—假设—动作—结果证据—适用边界—下一轮验证”沉淀为可复用经验。

## 成品周报结构（v4）

1. 本周经营总览：只陈述可由数据确认的整体结果。
2. 核心经营数据：程序生成的周度事实底座。
3. 本周问题与机会复盘结论：说明变化、因果链、证据与可信边界；不出现调查问题。
4. 经验沉淀：没有动作和结果证据时不强制形成经验。
5. 下一步动作：独立于事实分析，不混入因果结论。
6. 数据图表、完整明细与口径：默认折叠；渠道结构、完整日趋势、次卡、播控和来源均保留在此。

正文不再固定铺开“每店一段、每渠道一段、七天明细一段”。只有达到阈值的内容才进入正文；未触发的维度没有被删除，只是降级为附录证据。
