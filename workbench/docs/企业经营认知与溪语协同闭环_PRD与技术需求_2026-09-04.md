## 1. 产品定义

### 1.1 一句话定义

建立一套会持续认识企业、主动补齐经营认知、提出有依据的方案、在用户确认后推动执行，并根据结果修正知识与经验的 AI 原生经营辅助系统。

### 1.2 要解决的核心问题

企业经营辅助能力不足，通常不是因为模型不会写建议，而是因为系统缺少以下基础：

1. 不知道企业真实由哪些业务对象、能力、资源、约束和关系组成；
2. 数据、口头判断、原因假设和正式经验混在一起，无法判断什么能信；
3. 大量隐性知识散落在不同人员脑中，靠一次访谈或填表无法完整获得；
4. 建议与执行系统断开，用户看完以后无法持续推进；
5. 执行结果没有回到原问题和原假设，经验不会真正增长；
6. 普通知识采集方式枯燥、打扰强，员工不愿长期输入。

### 1.3 产品最终价值

系统最终应形成三个连续能力：

- **认识企业**：形成带来源、范围、时间、权限和证据状态的企业经营认知；
- **辅助判断**：发现值得关注的问题、机会和认知缺口，提出有业务依据的方案；
- **推动行动**：经用户确认后交给人员、飞书或 WorkBuddy 执行，并用结果更新判断与经验。

### 1.4 用户直接感知的服务

底层可以复杂，但普通使用者主要只应感知两项服务：

1. 溪语会在合适的时候陪用户看一件真正值得关注的经营事项，或自然地问一个确实影响判断的问题；
2. 用户认可建议后只需确认一次，系统即可安排后续执行，并在产生结果后回来说明进展和结论。

### 1.5 非目标

第一阶段明确不做：

- 不把溪语改造成日报机器人、调查问卷或企业监控工具；
- 不把所有聊天原文上传到企业知识库；
- 不让模型自动宣布因果成立或直接发布正式经验；
- 不让模型绕过授权执行高风险外部动作；
- 不为追求“智能”一次性引入复杂多 Agent、图数据库或向量数据库；
- 不重写现有周报、机会、打法、验证、经验和飞书取数能力；
- 不把 Codex 对话中的临时上下文写死进产品；
- 不要求普通运营人员维护技术化知识图谱。

## 2. 总体设计原则

### P-01 一个经营认知底座

项目、门店、指标、目标、决策、事实、知识缺口、机会、打法、验证、经验、任务和结果使用统一对象协议，通过稳定 ID 和关系连接。不能为溪语另建一套与企业认知底座互不相认的“工作记忆库”。

企业认知层在**逻辑上是独立领域**：工作台、溪语、飞书适配器和 WorkBuddy 都是它的生产者或消费者，不应把认知协议设计成某一个页面的内部数据结构。当前阶段为降低部署和维护成本，它仍然物理部署在工作台后端、复用现有存储与鉴权；模块接口必须保持中立，未来可在不改变上层产品协议的情况下独立部署。

### P-02 两套记忆严格分离

- 私人关系记忆归溪语：情绪、偏好、关系状态、生活经历、互动方式；
- 企业工作记忆归企业认知层，由工作台负责正式管理：经营事实、业务判断、项目变化、经验、任务与结果；
- 混合对话必须拆分后分别处理，原始整句不得同时进入两边。

### P-03 模型不是事实库

模型负责理解、关联、提炼、分析、规划和表达；程序负责身份、权限、数值、状态、版本、证据边界、幂等和审计。

### P-04 候选先于正式资产

对话提取、AI 分析和外部执行返回的内容，默认都是候选或证据，不得直接升级为确认事实、确认因果或正式经验。

### P-05 主动触达由价值驱动

溪语不能因为字段为空就提问。只有回答会明显改善当前判断、执行或验证时，才产生主动对话任务。

### P-06 一条主线，不堆零散模块

所有新增能力必须服务于同一闭环：

```text
来源与人员
→ 企业经营认知
→ 问题 / 机会 / 知识缺口
→ 溪语对话或工作台分析
→ 候选知识 / 方案
→ 人工确认
→ 飞书 / WorkBuddy / 人员执行
→ 结果与证据
→ 验证
→ 经验和认知更新
```

### P-07 人格只控制交流，不控制事实

溪语人格决定怎么说、何时说、是否适合追问；企业上下文和权限决定能说什么、能做什么。人格不能改写数值、来源、状态或执行权限。

### P-08 渐进式改造

优先复用现有接口、存储适配、主动消息、候选箱、打法和验证对象。仅在现有对象无法表达业务语义时新增能力，避免平行重建。

## 4. 系统角色与责任边界

### 4.1 企业认知层：共享经营世界模型

负责：

- 统一表达企业对象、关系、目标、事实、判断、能力、约束、决策、行动和结果；
- 保存每条认知的来源、范围、时间、证据状态、版本和权限；
- 为工作台、溪语和执行器提供中立的查询、候选提交、状态和审计协议；
- 通过 Context Compiler 为不同任务组装最小可信上下文；
- 维护冲突、过期信息和未知项，不把所有内容压成“知识正文”。

不负责：

- 代替工作台决定当前经营分析和页面流程；
- 溪语的人格、情绪和私人关系记忆；
- 直接操作所有第三方软件；
- 保存无关私人对话原文。

部署原则：当前阶段作为工作台后端内部的独立领域模块运行，使用中立 Schema、Port/Adapter 和 API；不单独新增服务器或数据库。未来若需要拆出服务，上层接口和业务对象不得随部署方式变化。

### 4.2 工作台：经营分析与决策控制面

负责：

- 管理项目档案、周数据、经营事实、机会、打法、验证和经验的正式业务流程；
- 基于企业认知层发现问题、机会和阻塞性知识缺口；
- 判断哪些事项值得触达、分析或执行；
- 提供候选审核、人工决策、执行审批和结果复盘页面；
- 将正式业务状态和人工决定写回企业认知层。

工作台是当前最主要的企业认知生产者和管理入口，但不是企业认知协议本身；未来其他应用可以在授权范围内直接使用同一认知层。

### 4.3 溪语：关系型交互与隐性知识触手

负责：

- 保持既有人格、关系感和情绪价值；
- 识别工作、生活和混合对话；
- 按需读取工作台提供的有限上下文；
- 在合适时机自然表达一项经营提醒或提出一个问题；
- 将用户回答提取为企业候选信息；
- 将用户的确认、拒绝、延后和修正回传工作台；
- 在任务有结果时，以人格化方式告知用户。

不负责：

- 保存企业正式事实；
- 自动确认因果；
- 自动发布经验；
- 在没有工作台资料时凭私人记忆编造经营事实；
- 自行决定高风险外部执行。

### 4.4 WorkBuddy：执行适配器

负责：

- 接收已经批准的结构化执行任务；
- 调用网页、软件、文件、CLI 或 API；
- 返回步骤、产物、失败原因和可核验结果；
- 在需要额外授权、选择或高风险写入时暂停并请求人工处理。

不负责：

- 成为企业知识主库；
- 自行把执行结果宣布为经营经验；
- 绕过工作台的动作权限和审批要求。

### 4.5 飞书：协作与正式业务触点

负责：

- 经营数据来源与周报落盘；
- 任务、日程、审批、通知和人员协作；
- 可选的经验阅读镜像与灾备；
- 将任务状态、评论、完成事件回传工作台。

飞书不是全部经营逻辑的主库。状态判断、知识等级和经验是否可调用仍由工作台控制。

### 4.6 模型 API：可替换推理能力

负责：分类、提取、相关性判断、缺口判断、方案生成、表达、复盘和结构化输出。

不得拥有：最终事实权、正式状态变更权、无限工具权限、跨用户越权检索能力。

## 5. 用户角色与权限

### 5.1 角色

| 角色 | 主要权限 |
|---|---|
| 执行者 | 查看本人和授权范围信息，回答问题，确认自己的事实和执行进展 |
| 运营管理者 | 查看授权门店/项目，审核候选，选择机会和方案，批准普通执行 |
| 经营审核者 | 确认因果结论、验证结论和正式经验发布 |
| 系统管理员 | 管理账号绑定、项目/门店权限、连接器和高风险动作权限 |

第一阶段同一真实用户可以同时拥有多个角色，不要求立即提供组织内所有人员姓名。

### 5.2 权限要求

- AUTH-01：每个溪语账号必须绑定 `organizationId`、`actorId` 和允许访问的项目/门店；
- AUTH-02：读取权限与写候选权限分开；
- AUTH-03：批准执行、发布经验、修改档案分别配置；
- AUTH-04：连接器只能拿到完成任务所需的最小权限；
- AUTH-05：所有工具调用必须记录发起人、批准人、作用范围和结果；
- AUTH-06：私人对话和企业资产不能因管理员权限而默认互相开放。

## 6. 企业经营认知模型

### 6.1 核心对象

第一阶段支持以下对象类型，不要求同时制作全部管理页面：

| 类别 | 对象 | 示例 |
|---|---|---|
| 组织 | organization、department、role、person | 公司、运营部、店长、某位运营者 |
| 经营范围 | project、venue | VR 项目、东坝店、中影店 |
| 业务资源 | product、channel、partner、resource、capacity | 次卡、抖音、科技馆、场地容量 |
| 经营定义 | metric、business_rule、decision_policy | 接待客流、目标完成率、审批规则 |
| 经营记录 | operating_fact、external_event、decision | 客流变化、商圈活动、调整定价决定 |
| 认知过程 | claim、hypothesis、knowledge_gap、conflict | 运营判断、原因假设、缺失信息 |
| 改进闭环 | opportunity、tactic、validation、experience | 机会、打法、验证、正式经验 |
| 协同执行 | conversation_task、execution_task、execution_result | 溪语追问、飞书任务、执行结果 |

第一阶段不要求给全部对象制作录入页面，但统一协议和 normalizer 必须实际覆盖以下最小核心集合：

```text
project / venue / metric
goal / decision
operating_fact / claim / hypothesis / conflict
opportunity / tactic / validation / experience
```

其中 `goal` 和 `decision` 是一级对象，不能只藏在项目档案或周报正文里：

- `goal` 至少记录目标内容、优先级、适用范围、生效期、成功指标和提出/确认者；
- `decision` 至少记录最终选择、决定人、决定时间、依据、被放弃的备选项、原因和后续动作；
- 旧数据没有结构化目标或决策时可以返回空集合或 `legacy_unverified`，不得由 AI 补造；
- 第一阶段只要求对已有可识别内容做读取映射，不要求一次性补录企业全部历史决策。

### 6.2 关系类型

第一阶段至少支持：

```text
belongs_to          属于项目/组织/门店
applies_to          适用于
owned_by            负责人
depends_on          依赖资源、人员或前置任务
influences          可能影响指标，不代表已证实因果
supports            证据支持
contradicts         与另一信息冲突
derived_from        从数据、对话或分析派生
tests               验证某个假设
executes             执行某个打法
produces            产生结果或产物
supersedes          替代旧版本
learned_as          经验证沉淀为经验
```

`influences`、`supports` 和 `causes` 不得混用。第一阶段不设置可由普通对话直接生成的 `causes` 关系；确认因果必须经过审核或验证。

### 6.3 所有认知记录的统一外壳

```json
  "id": "stable-id",
  "recordType": "operating_fact",

    "organizationId": "org-yuanqu",

    "venueIds": ["ZHONGYING"],
    "departmentIds": [],
    "actorIds": []

  "statement": "本周科技馆客流明显回落",
  "timeRange": {
    "start": "2026-08-15",
    "end": "2026-08-21",
    "precision": "week",
    "effectiveUntil": null
  },
  "epistemicStatus": "operator_observation",
  "lifecycleStatus": "active",
  "sourceRefs": ["xiyu-turn:..."],
  "evidenceRefs": [],
  "relatedRefs": ["venue:ZHONGYING", "partner:SCIENCE_MUSEUM"],
  "ownerActorId": "actor-...",
  "confidence": 0.78,
  "sensitivity": "internal",
  "version": 1,
  "createdAt": "ISO-8601",
  "updatedAt": "ISO-8601"
}
```

### 6.4 认识状态与业务状态分离

`epistemicStatus` 表示“我们凭什么相信它”：

```text
system_measurement       系统数据
confirmed_background     人工确认背景
operator_observation     运营者观察
operator_claim           运营者判断
hypothesis               待验证假设
supported_hypothesis     有证据支持但未确认
confirmed_conclusion     已审核结论
validated_experience     已验证经验
conflicted               存在冲突
unknown                  尚不知道
```

`lifecycleStatus` 表示“这条内容现在是否生效”：

```text
draft → active → superseded / expired / rejected / archived
```

REQ-COG-01：程序不得根据置信度数字自动把 hypothesis 升级为 confirmed_conclusion。  
REQ-COG-02：所有记录必须有作用范围和来源。  
REQ-COG-03：范围不明时保留 unknown，禁止自动套用默认门店。  
REQ-COG-04：存在矛盾时同时保留双方来源，生成 conflict，不静默覆盖。  
REQ-COG-05：被新版本替代的内容仍可追溯，但默认不进入当前上下文。  
REQ-COG-06：涉及人员观点时必须保留“谁在什么角色下表达”，不能合成为匿名企业事实。  
REQ-COG-07：目标必须是有生效期和适用范围的一级对象，不能仅作为分析提示词中的一句文字。  
REQ-COG-08：经营决策必须记录依据、选择、决定人和被放弃的主要备选项，使系统能够理解“为什么这样决定”。  
REQ-COG-09：第一阶段企业认知层只建立统一读取模型，不复制现有正式资产形成第二主库。

## 7. 知识缺口系统

知识缺口不是普通空字段，而是“缺少后会妨碍某个判断或行动的信息”。

### 7.1 数据结构

```json
{
  "schemaVersion": "knowledge-gap-v1",
  "id": "kg_...",
  "scope": { "projectId": "yuanqu-vr", "venueIds": ["ZHONGYING"] },
  "question": "科技馆客流回落是否真正影响了门店可触达客流？",
  "whyNeeded": "影响本周客流下降原因判断和下一步渠道投入",
  "blockedObjectRefs": ["hypothesis:...", "opportunity:..."],
  "knownEvidenceRefs": ["fact:..."],
  "expectedAnswerType": "observation_or_metric",
  "candidateResponders": [{ "actorId": "...", "reason": "负责中影店现场运营" }],
  "priority": "high",
  "status": "open",
  "expiresAt": "2026-09-10T23:59:59+08:00",
  "createdBy": "weekly-analysis",
  "createdAt": "ISO-8601"
}
```

### 7.2 状态

```text
open
→ scheduled
→ asking
→ answered
→ resolved / partially_resolved / no_answer / obsolete
```

### 7.3 需求

- REQ-GAP-01：缺口必须关联被它阻塞的判断、机会、打法或验证；
- REQ-GAP-02：缺口必须说明答案的用途，禁止为“完善资料”泛泛提问；
- REQ-GAP-03：每个用户同时活跃的高优先级缺口默认不超过 3—5 个；
- REQ-GAP-04：系统应记录候选回答者及原因，但不得仅凭姓名猜测职责；
- REQ-GAP-05：过期、已解决和低价值缺口不得继续触达；
- REQ-GAP-06：同一缺口重复出现时合并来源和阻塞对象，不重复建项；
- REQ-GAP-07：用户说“不知道”也是有效结果，应转交其他来源或降级，不连续逼问。

## 8. 主动对话任务

### 8.1 产品定义

主动对话任务是工作台交给溪语的一项有限沟通任务。它不是一条通知文本，而是带目标、依据、问题、等待回答和完成条件的业务对象。

### 8.2 首批允许触发的三类任务

1. `important_signal`：重要异常或机会，需要用户看见或补充事实；
2. `validation_due`：正在执行的验证到了复盘节点，需要实际进展或结果；
3. `knowledge_gap`：一个高价值缺口正在阻塞判断或行动。

第一阶段禁止由系统自动发送泛化“今日灵感”、空洞行业资讯或没有明确对象的闲聊式经营建议。

### 8.3 数据协议

```json
{
  "schemaVersion": "business-conversation-task-v1",
  "id": "bct_...",
  "taskType": "knowledge_gap",
  "actorId": "xiyu-account-binding",
  "scope": { "projectId": "yuanqu-vr", "venueIds": ["ZHONGYING"] },
  "goal": "补齐中影客流下降的现场影响因素",
  "whyNow": "本周周报因果判断受阻，且两天后需要确定下周动作",
  "knownFacts": ["科技馆客流明显回落", "中影接待客流环比下降"],
  "knowledgeGapRef": "kg_...",
  "sourceRefs": ["fact:...", "signal:..."],
  "questionIntent": "询问本周现场是否还有活动、排班、动线或竞品变化",
  "expectedOutput": "一条或多条可确认现场事实，或明确没有其他变化",
  "doNotAssume": ["科技馆客流回落已经被证明是唯一原因"],
  "priority": "high",
  "status": "pending",
  "notBefore": "ISO-8601",
  "expiresAt": "ISO-8601",
  "createdAt": "ISO-8601"
}
```

### 8.4 状态机

```text
draft
→ pending
→ selected
→ delivered
→ awaiting_answer
→ answered
→ candidate_extracted
→ resolved / partially_resolved

任意有效阶段
→ deferred / dismissed / expired / failed
```

### 8.5 触达选择规则

- REQ-CONV-01：同一用户默认每天最多一个主动经营对话任务；
- REQ-CONV-02：先经过权限、重复、过期、免打扰和当前情绪/会话状态过滤；
- REQ-CONV-03：排序主要考虑经营影响、时间紧迫性、信息价值、回答成本和近期打扰；
- REQ-CONV-04：触达文本由溪语主模型基于现有人格生成，不保存写死话术；
- REQ-CONV-05：一次只表达一个目标，最多提出一个核心问题；
- REQ-CONV-06：用户正在表达明显情绪、拒绝工作或处于免打扰时延后，不强行插入；
- REQ-CONV-07：任务发送后必须写入当前会话的 active business task，不能只标记 delivered；
- REQ-CONV-08：下一条相关回答优先回绑 active task；无法判断时生成待确认关联，不得猜；
- REQ-CONV-09：回答完成后提取候选，并更新原缺口和原业务对象；
- REQ-CONV-10：用户拒绝、延后、不知道或转话题时必须形成明确状态，不继续追问；
- REQ-CONV-11：同一事实已经从系统数据获得时，不再向用户询问；
- REQ-CONV-12：工作台不可用时不得发送依赖工作台事实的主动经营消息。

### 8.6 溪语可见表达要求

溪语应先让用户知道“发生了什么或为什么值得看”，再提出最低成本的下一步。不得暴露任务 ID、置信度和系统字段。

允许：

> 我刚看中影这周客流掉得挺明显，科技馆那边也在掉。不过我有点拿不准是不是只有这个原因——店里这周有没有什么和平时不一样的？

不允许：

> 检测到知识缺口 KG-102，请补充本周经营事实。

### 9.1 候选类型

### 9.3 类型化应用规则

| 候选类型 | 确认后的正式去向 | 额外要求 |
|---|---|---|
| 现场可观察事实 | 经营事实 | 用户确认作用范围和时间 |
| 档案修订 | 项目/门店档案新版本 | 不反向修改历史档案快照 |
| 运营判断/原因解释 | claim/hypothesis | 不得直接成为确认因果 |
| 机会 | 机会台账 | 需要关联证据和影响对象 |
| 打法想法 | 打法候选 | 进入打法方案既有流程 |
| 验证进展 | 对应验证记录 | 必须可靠关联原验证 |
| 结果陈述 | 结果证据候选 | 指标可由系统核对时优先核对 |
| 经验候选 | 经验候选区 | 必须经过验证和发布审核 |
| 决策规则 | decision_policy 草稿 | 需要管理者审核 |
| 能力/约束 | capability/constraint | 需要对象负责人确认 |

### 9.4 需求

- REQ-CAND-01：候选保留最小业务原文片段，不保存无关私人内容；
- REQ-CAND-02：同一对话任务的回答与候选必须双向可追溯；
- REQ-CAND-03：确认动作必须显示将写入哪里、作用范围和会影响什么；
- REQ-CAND-04：驳回候选需保留抑制指纹，避免再次生成相同垃圾候选；
- REQ-CAND-05：冲突不能通过“最后一次回答”覆盖旧内容；
- REQ-CAND-06：应用成功后更新原知识缺口为 resolved 或 partially_resolved；
- REQ-CAND-07：通用 `intelligenceAssets` 可保留为索引，但不能替代正式类型对象；
- REQ-CAND-08：经验候选确认后仍保持 `retrievalEligible=false`，直到验证和审核完成。

## 10. 经营建议、灵感与方案

### 10.1 产品关系

“经营灵感”不是独立内容流，而是经营机会探索的一种低承诺入口。

```text
灵感
→ 用户表示感兴趣
→ 打法候选
→ 补齐适用范围、目标、投入和约束
→ 完整打法
→ 验证 / 执行
```

### 10.2 建议质量要求

每条正式建议至少应包含：

- 观察到的问题或机会；
- 与当前企业/门店的关联依据；
- 哪些部分是事实，哪些是推断；
- 需要利用的企业能力和资源；
- 关键约束与风险；
- 可选择的一到三个方案方向；
- 预期收益机制，而非无依据承诺 ROI 翻倍；
- 最小可执行下一步；
- 需要验证的关键假设。

### 10.3 需求

- REQ-IDEA-01：经营灵感被用户选择后必须出现在既有“打法候选”入口；
- REQ-IDEA-02：灵感、问题、机会和打法使用关系连接，不复制多份相同正文；
- REQ-IDEA-03：没有经营数据时可以做业务结构想象，但必须明确依据是档案/能力而非本周表现；
- REQ-IDEA-04：外部案例未来作为可选证据源，未配置搜索时不得伪装已有同行证据；
- REQ-IDEA-05：AI 可以提出突破性方案，但必须标注所需能力、未知条件和验证路径；
- REQ-IDEA-06：所有建议从统一 Context Compiler 获取上下文，不在提示词中硬编码企业事实。

## 13. Context Compiler：统一上下文编译

### 13.1 目的

所有 AI 任务都从同一服务按任务目标组装最小、可信、可追溯的上下文。不得让周报、经营灵感、溪语和打法生成分别维护一套互相漂移的上下文逻辑。

### 13.2 输入

```text
actorId
taskType
scope
timeRange
goal/query
requestedAssetTypes
token/character budget
```

### 13.3 编译顺序

1. 身份和权限过滤；
2. 项目、门店、人员和业务对象范围过滤；
3. 时间有效性和版本过滤；
4. 认识状态过滤；
5. 根据任务目标补充关系邻居；
6. 收集支持证据、反证、冲突和未知项；
7. 相关性排序；
8. 在预算内生成结构化上下文包；
9. 保存 fingerprint 和实际引用记录。

### 13.4 输出

```json
{
  "schemaVersion": "enterprise-context-v2",
  "task": { "type": "opportunity_analysis", "goal": "..." },
  "scope": {},
  "objects": [],
  "goalsAndDecisions": [],
  "confirmedFacts": [],
  "claimsAndHypotheses": [],
  "capabilitiesAndConstraints": [],
  "activeWork": [],
  "publishedExperiences": [],
  "supportingEvidence": [],
  "counterEvidence": [],
  "conflicts": [],
  "missingInformation": [],
  "boundaries": [],
  "fingerprint": "..."
}
```

### 13.5 需求

- REQ-CTX-01：正式经验仅在 `published && retrievalEligible` 时进入经验区；
- REQ-CTX-02：进行中验证只能进入 activeWork；
- REQ-CTX-03：历史背景可以解释相关性，但不能充当本周因果证据；
- REQ-CTX-04：每个上下文项包含 ID、版本、来源和认识状态；
- REQ-CTX-05：任务目标不同，召回组合不同；不能每次塞入整个企业库；
- REQ-CTX-06：存在明显反证或冲突时必须随支持材料一起提供；
- REQ-CTX-07：无匹配资料时明确返回缺口，不由模型自行补全；
- REQ-CTX-08：第一阶段继续采用结构过滤和轻量检索；达到数百条有效资产且召回出现可测问题后再评估向量检索。
- REQ-CTX-09：分析任务必须按范围返回当前有效目标和相关历史决策；没有结构化目标或决策时明确为空，不使用模型常识代填。
- REQ-CTX-10：Context Compiler 通过中立 Port 读取来源，不直接依赖具体页面结构；当前可由工作台后端提供 Port 实现。

## 14. AI 与提示词架构

### 14.1 任务拆分

| AI 任务 | 是否面向用户 | 主要职责 |
|---|---|---|
| work-context-router | 否 | personal/work/mixed、范围和检索意图 |
| context-relevance-ranker | 否，可选 | 在程序过滤后的资产中排序 |
| knowledge-gap-evaluator | 否 | 判断缺口是否高价值、适合问谁 |
| conversation-task-planner | 否 | 将业务事件变成单目标对话任务 |
| 溪语主回复 | 是 | 保持人格完成交流、提醒或追问 |
| work-intelligence-extractor | 否 | 从工作片段提取候选信息 |
| opportunity/tactic analyzer | 否/由工作台展示 | 生成机会和打法候选 |
| result-reviewer | 否/由工作台展示 | 分析结果、偏差和干扰因素 |

### 14.2 提示词要求

- REQ-AI-01：提示词在 Prompt Registry 中版本化，不散落成大量业务字符串；
- REQ-AI-02：项目、门店、指标、角色、事实和工具目录在运行时注入，不写死；
- REQ-AI-03：所有非聊天任务使用 JSON Schema 结构输出；
- REQ-AI-04：系统保存模型、参数、Prompt 版本、上下文 fingerprint、原始输出和校验结果；
- REQ-AI-05：资料块明确是数据而非指令，防止企业文档改变系统规则；
- REQ-AI-06：生成建议必须区分事实、推断、假设和未知项；
- REQ-AI-07：表达人格与事实内容分离；必要时使用“事实锁定 + 人格润色 + 数值校验”的现有模式；
- REQ-AI-08：模型失败时不推动正式状态；可回退为规则结果或明确失败；
- REQ-AI-09：简单路由、提取和分类优先使用低延迟模型；复杂方案和复盘再使用强模型；
- REQ-AI-10：第一阶段优先一个主 Agent 配合清晰工具，只有持续出现工具误选或提示词复杂度失控时才拆多 Agent。

### 14.3 溪语主动表达补充模块

此模块追加到溪语现有人格 Prompt，而不是替换人设：

```text
你收到的是一项已经由企业系统筛选过的经营对话任务。
保持当前人格、关系和自然语气。
先说清楚为什么这件事现在值得关注，再完成一个沟通目标。
一次最多问一个核心问题；不要像表单、审计、日报或客服。
knownFacts 可以直接引用，但 doNotAssume 中的内容不得当成事实。
如果用户不想聊、情绪不适合或明确延后，应自然收住，并返回对应状态。
不得替用户确认因果、批准执行或发布经验。
```

- 可选的调试模式显示本轮是生活/工作/混合、使用了多少企业资料、关联了哪个对话任务、产生了多少候选；

## 17. 存储、版本和迁移

### 17.1 第一阶段存储策略

继续采用当前免费 EdgeOne 环境和现有 runtime-state/Blob adapter，不要求注册新数据库。新增对象按类型独立存储，避免继续扩大单个 `workbench` 对象：

```text
cognition-records
knowledge-gaps
conversation-tasks
execution-tasks
execution-results
integration-bindings
integration-audit
```

本地开发可使用同构 JSON repository；线上使用 Blob repository。业务代码不能依赖具体文件路径。

### 17.2 ID 规则

- 所有对象使用稳定机器 ID；
- 人类名称只作展示，不参与跨系统主键；
- 门店新增仅创建新 `venue` 实例和绑定，不修改各模块硬编码；
- 外部飞书任务、WorkBuddy 任务保存 `externalRef`，但不取代内部 ID。

### 17.3 迁移

1. 为现有项目、门店、事实、机会、打法、验证、经验建立对象引用；
2. 先保持原页面和原 runtime-state 可读写；
3. 新能力双写关系索引，但正式内容仍由原模块服务写入；
4. 对比新旧读取结果；
5. 验收后逐模块切换读取；
6. 保留旧结构只读回退至少一个版本。

不得在迁移中把历史 AI 文字自动认定为正式事实。无法判断的内容标记为 `legacy_unverified`。

## 18. 触发器与调度

### 18.1 程序触发器

第一阶段实现三类确定性扫描器：

1. 周数据/日数据刷新后，检查重要异常和高价值机会；
2. 验证项目到达观察日或超过预定进度；
3. 新增分析、候选或冲突后，检查是否产生阻塞性知识缺口。

扫描器只产生候选任务，不直接发消息。

### 18.2 AI 价值判断

AI 对候选任务判断：

- 回答后是否会改变判断或行动；
- 是否已有其他更可靠来源；
- 用户是否适合回答；
- 回答成本是否合理；
- 是否可以合并到正在进行的相关对话；
- 是否值得在截止时间前主动打扰。

程序随后执行权限、频率、去重、冷却和状态校验。AI 无权绕过程序闸门。

### 18.3 调度要求

- REQ-TRG-01：生产主动功能继续默认关闭，完成真实账号绑定和小范围验收后逐用户开启；
- REQ-TRG-02：任务选择复用溪语现有主动时机和免打扰能力；
- REQ-TRG-03：企业任务优先级不能无限覆盖情绪安全和用户明确拒绝；
- REQ-TRG-04：同一事项在没有新信息时不得重复发送；
- REQ-TRG-05：任务过期、对象关闭或信息已补齐时自动取消；
- REQ-TRG-06：调度和发送分别记录，便于判断是“没选中”还是“发送失败”。

## 20. 安全、隐私与审计

- REQ-SEC-01：默认只传工作相关最小片段，不传完整私人会话；
- REQ-SEC-02：用户可即时声明本段不进入企业候选；
- REQ-SEC-03：私人关系记忆与企业工作记忆使用不同存储和访问接口；
- REQ-SEC-04：企业文档按数据处理，防止提示注入；
- REQ-SEC-05：服务凭证不下发浏览器；
- REQ-SEC-06：所有正式写入和工具动作记录来源、操作者、批准人、输入摘要、结果和时间；
- REQ-SEC-07：高风险、不可逆、涉及资金或公开发布的动作必须人工批准；
- REQ-SEC-08：审计日志不保存无关私人正文；
- REQ-SEC-09：员工能查看溪语近期提取的本人业务候选并申请删除未正式采用内容；
- REQ-SEC-10：跨角色汇总时遵守原始信息权限，不能因进入企业认知底座而扩大访问范围。

## 21. 非功能要求

### 21.1 性能

- 工作语境路由目标 P95 小于 1.5 秒；
- Context Compiler 结构检索目标 P95 小于 800 毫秒；
- 新知提取异步执行，不增加主回复等待；
- 主动任务生成不阻塞工作台页面；
- 同一工作语境可缓存目录和 fingerprint，避免每轮全量读取。

### 21.2 可靠性

- 工作台不可用时溪语私人聊天继续；
- 候选写入失败进入现有 outbox 并幂等重试；
- 主动消息发送失败不把任务标记为 delivered；
- 回答提取失败保留 answered 状态和最小原文引用，可重试；
- 外部执行器断开时任务保持可恢复状态；
- 正式状态更新采用版本冲突检测。

### 21.3 可观测性

每次链路记录：

```text
触发器
→ 候选任务
→ 选择/抑制原因
→ 发送结果
→ 回答绑定
→ 候选提取
→ 人工处理
→ 正式写入
→ 执行和结果
```

不得只记录“模型调用成功”，而看不到业务对象是否真正闭环。

## 22. 产品指标与验收指标

### 22.1 不以消息量衡量成功

主动消息越多不代表越成功。首期关注：

| 指标 | 定义 |
|---|---|
| 有效触达率 | 用户愿意回答、确认有用或采取后续动作的任务占比 |
| 打扰率 | 用户拒绝、认为无关、重复或要求不要再问的占比 |
| 候选采纳率 | 对话候选被确认并正式应用的占比 |
| 缺口解决率 | 主动对话实际解决或部分解决的高价值缺口占比 |
| 回绑成功率 | 用户回答能自动关联正确任务的占比 |
| 错误事实率 | 回复引用错误范围、过期或未经确认内容的占比 |
| 行动转化率 | 建议进入打法、任务或验证的占比 |
| 结果回收率 | 已执行任务中回收到结果和证据的占比 |
| 经验升级率 | 完成验证后形成正式经验的占比，不追求越高越好 |
| 认知新鲜度 | 核心档案和约束在有效期内的占比 |

### 22.2 一期业务成功标准

用一个真实使用者、一个真实项目、一个或两个门店连续试用至少一周：

- 不影响生活聊天和既有人格体验；
- 每天最多一项经营触达，用户认为大部分确实值得回答；
- 至少一条隐性知识经确认进入正式经营对象；
- 至少一个知识缺口从产生到解决完整闭环；
- 至少一个方案进入执行任务并回收真实结果；
- 无私人内容误入企业库、无未验证经验被当作正式经验调用；
- 所有事实和状态可追溯到来源与版本。

- [ ] S2-01 固定试验问题、门店、回答者、当前事实、一个关键缺口和成功标准；
- [ ] S2-02 建立最小 knowledge-gap 对象和持久化；
- [ ] S2-03 将一个现有 enterprise event 映射为 conversation task；
- [ ] S2-04 复用溪语主动消息链完成一次触达，并保存 active business task；
- [ ] S2-05 将用户回答可靠回绑原任务，生成带 gapRef 的候选；
- [ ] S2-06 人工确认候选后更新正确认知对象，并关闭或部分关闭 Gap；
- [ ] S2-07 使用新上下文重新生成经营判断和一个行动建议；
- [ ] S2-08 建立最小 execution-task，第一轮允许由人执行，不强制接 WorkBuddy；
- [ ] S2-09 回收实际动作、结果、指标和干扰因素，并挂回原判断/验证；
- [ ] S2-10 生成不可直接检索的经验候选，完成真实业务验收与测试数据恢复。

验收：一个真实案例能够从问题开始，经过一次有价值的溪语沟通和一次实际行动，回收到结果并更新企业认知；任务完成不会自动被判定为经验成立。

### 阶段 3：知识缺口与主动对话能力通用化

目标：把阶段 2 的单案例实现抽象为可复用能力，而不是为一个门店或一句问题写死流程。

- [ ] S3-01 完成 knowledge-gaps repository、API 和完整状态；
- [ ] S3-02 将现有 events 通用映射为 conversation tasks；
- [ ] S3-03 完善 `awaiting_answer/answered/resolved/partially_resolved/expired/failed` 等状态；
- [ ] S3-04 完善下一轮回答回绑、不确定关联和人工纠正；
- [ ] S3-05 候选、任务、缺口和认知对象之间全部使用稳定引用；
- [ ] S3-06 完成拒绝、延后、不知道、转话题、过期和失败处理；
- [ ] S3-07 增加工作台主动协同调试入口，并用至少三个不同业务案例回归。

验收：不同门店、不同问题类型都能复用同一套任务和回绑机制，不依赖特定关键词或固定案例。

### 阶段 4：有限自动触发与价值排序

目标：让系统能主动发现少量真正值得沟通的事项。

- [ ] S4-01 实现重要经营信号触发器；
- [ ] S4-02 实现验证到期触发器；
- [ ] S4-03 实现阻塞性知识缺口触发器；
- [ ] S4-04 实现 AI 价值判断和程序硬闸；
- [ ] S4-05 实现每日上限、冷却、重复和过期；
- [ ] S4-06 逐账号开启生产开关，不全量启用；
- [ ] S4-07 建立有效触达率和打扰率统计。

验收：连续一周没有无目标泛问；同一事项无变化时不重复；用户明确拒绝后停止。

### 阶段 5：经营建议与打法主线融合

目标：让经营灵感从一次性内容变成可以继续推进的方案入口。

- [ ] S5-01 灵感、问题、机会、打法使用对象引用；
- [ ] S5-02 “感兴趣/进入打法候选”后可在打法方案页找到；
- [ ] S5-03 方案生成读取企业能力、约束、决策目标和正式经验；
- [ ] S5-04 方案展示事实、推断、未知项、收益机制和最小下一步；
- [ ] S5-05 对有想象力的方案增加能力差距和验证路径；
- [ ] S5-06 从打法生成 execution-task 草稿。

验收：用户从一条灵感进入打法、补齐方案并生成执行草稿，全程只有一个主对象链，不出现两套规则。

### 阶段 6：飞书执行与结果回流

目标：在阶段 2 已经验证行动闭环成立后，用现有飞书基础替代手工执行记录。

- [ ] S6-01 完善 execution-task repository、状态机和审批；
- [ ] S6-02 实现飞书 task adapter；
- [ ] S6-03 创建、查询和更新飞书任务；
- [ ] S6-04 接收完成/失败/评论事件；
- [ ] S6-05 生成 execution-result 并回绑验证；
- [ ] S6-06 溪语主动告知结果或需要补充的信息；
- [ ] S6-07 验证结果进入既有经验候选流程。

验收：一个已批准打法可以创建真实飞书任务，完成后系统自动获取结果，工作台完成验证复盘，溪语向用户反馈。

### 阶段 7：WorkBuddy 执行适配

目标：在统一协议稳定后，再增加第二类执行器。

- [ ] S7-01 定义 WorkBuddy capability catalog；
- [ ] S7-02 实现 adapter 和签名回调；
- [ ] S7-03 选择 1—2 个低风险真实任务；
- [ ] S7-04 实现暂停、人工接管、失败和结果证据；
- [ ] S7-05 与飞书执行使用同一状态和展示；
- [ ] S7-06 完成权限和不可逆动作回归。

验收：同一类执行任务可以根据 executorType 路由，工作台和溪语不需要理解执行器内部细节。

### 阶段 8：多角色企业全景与认知治理

目标：不同角色的信息可以组合，但不混淆来源、权限和冲突。

- [ ] S8-01 增加人员、角色、部门和职责对象；
- [ ] S8-02 知识缺口可推荐回答者；
- [ ] S8-03 跨角色观点并列和冲突处理；
- [ ] S8-04 过期信息复核和定期刷新；
- [ ] S8-05 权限化跨部门汇总；
- [ ] S8-06 企业认知健康总览。

验收：两名角色对同一事项提供不同信息时，系统不覆盖、不越权，并能形成待核冲突或合并后的多来源结论。

## 24. 回归测试矩阵

每个阶段至少覆盖：

### 24.1 记忆与人格

- 纯生活对话不调用工作台；
- 纯工作对话使用企业资料但保持溪语人格；
- 混合对话只把工作片段送企业链；
- “先不聊工作”和“这段不要同步”即时生效；
- 企业事实不进入私人长期记忆。

### 24.2 范围和事实

- 单门店不串店；
- 多门店明确选择；
- 范围不明不猜；
- 测试记录不进入正式上下文；
- 数值查询返回真实数据且人格润色不改数值；
- 过期档案和被替代经验默认不召回。

### 24.3 主动对话

- 有高价值缺口才触达；
- 无变化不重复；
- 一个任务只问一个重点；
- 回答关联正确任务；
- 用户拒绝/延后/不知道均正确结束；
- 发送失败、提取失败、工作台不可用可恢复。

### 24.4 候选和知识

- 同义重复合并；
- 上升/下降等相反表述形成冲突；
- 拒绝后抑制重复；
- 作用范围和时间缺失时不猜；
- 候选应用到正确正式对象；
- 未验证经验不可检索。

### 24.5 执行和结果

- 未批准不执行；
- 低、中、高风险动作闸门正确；
- 执行状态不被提前说成完成；
- 失败不无限重试；
- 结果回绑原打法和验证；
- 任务完成不自动等同验证成功；
- 正式经验具有证据、范围和边界。

## 25. 迁移与回滚要求

- 每阶段修改前保存对应代码、配置和数据快照；
- 新 Schema 均带版本号并提供迁移函数；
- 新旧接口在切换期可并存，避免一次性同时升级两套项目；
- 所有生产主动触达和外部执行使用独立 feature flag；
- 回滚代码时不得覆盖测试期间新增的真实溪语消息；
- 回滚数据优先按对象 ID 精确恢复，不直接覆盖完整数据库；
- 飞书真实任务和外部动作无法随代码回滚，测试必须使用独立测试范围并记录清理方式。

## 26. 暂未决定但不阻塞前期的事项

7. 员工端对企业候选的告知和隐私政策文案。

## 27. 当前推荐的最先实施范围

第一轮不要直接做 WorkBuddy，也不要先大量自动推送。推荐先把底座统一，再立即跑一个真实纵向案例：

```text
阶段 0：保护现状
→ 阶段 1：统一认知协议与 Context Compiler
→ 阶段 2：一个真实业务案例的纵向闭环
```

这三步完成后，应能够用一个真实案例验证：

1. 企业认知层知道当前问题、目标、已有决定以及判断缺什么；
2. 工作台把一个明确任务交给溪语；
3. 溪语在保持人格的情况下自然询问；
4. 用户回答被绑定回原任务；
5. 回答只形成候选，不越权变成事实；
6. 人工确认后写入正确经营对象；
7. 原知识缺口被关闭；
8. 下一次经营分析能引用这条新知识并保留来源；
9. 系统基于更新后的判断提出一个可执行动作；
10. 人工批准后，第一轮允许线下执行并手工回填，不强制接入外部执行器；
11. 回收实际动作、结果指标和干扰因素；
12. 形成验证结论和不可直接检索的经验候选，并将新认知更新回原对象链。

只有一个真实案例从问题走到结果并完成认知更新后，才把知识缺口、主动对话、自动触发、经营方案和外部执行分别通用化。这样能先证明完整业务价值，也不会让未成熟的认知直接驱动更强的自动化。

## 28. 外部设计参考及取舍

本方案参考但不照搬以下思路：

- Palantir Ontology：用企业对象、关系、逻辑、动作和权限表达运行世界，而非只做文档检索；
- Glean Enterprise Graph：同步内容时同时考虑权限、活动和来源，使企业检索不越权；
- OpenAI Agent 工程实践：以模型、工具、指令和 guardrails 组成任务 Agent，先从单 Agent 和清晰工具开始，高风险动作保留人工介入。

参考链接：

- https://www.palantir.com/docs/foundry/ontology/overview
- https://www.palantir.com/docs/foundry/ontology/why-ontology
- https://docs.glean.com/get-started/setup/connect-data-sources
- https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/

这些参考只验证共同架构原则，不替代本项目的业务状态、产品体验和实施判断。
