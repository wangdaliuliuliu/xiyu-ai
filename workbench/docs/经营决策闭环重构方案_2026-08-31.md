# 经营决策闭环整体优化实施方案（最终确认版）

更新时间：2026-08-31  
适用项目：VR大空间经营策略工作台 / 周运营录入台

## 零、已经确认的实施基线

本方案后续实施不再重复向使用者询问服务器、数据库或目录选择，统一按以下基线执行：

1. 保持现有 EdgeOne Makers 免费部署，不升级服务器运行环境。
2. 使用 EdgeOne Blob 保存正式业务对象，不注册或维护外部数据库。
3. 东坝店、中影店以及以后新增门店均由统一门店模板创建；每家店的数据、档案、分析和周报通过稳定 `venue_id` 隔离。
4. 角色只定义权限，不要求现在提供人员姓名；当前单人账号可同时拥有全部权限。
5. 飞书继续承担经营事实取数/落盘、正式文档发布和平台外备份。
6. 本机飞书 CLI 用于首次创建备份目录和联调；线上自动备份由 EdgeOne Functions 调用飞书 API 完成，不依赖本机持续开机。
7. 经验的权威版本保存在 EdgeOne Blob；飞书文档或多维表格只是方便人阅读的发布镜像。

## 一、结论先行

本次不应继续在现有“周报页面”上叠加更多栏目，而应把系统的根结构调整为一套经营决策闭环：

> 经营事实 → 发现信号 → 调查因果 → 形成机会 → 设计验证 → 记录结果 → 沉淀经验 → 反哺下一轮经营

周报仍然保留，但它是这个闭环在某一周、某一门店的可读输出，不再承担事实库、问答记录、经验库和任务管理等全部职责。

建议同时确立三条底线：

1. **程序负责流程和事实，AI 负责受约束的分析任务。** AI 不能直接改变正式事实、机会状态或经验结论。
2. **EdgeOne Blob 中的结构化业务对象是经营资产主库。** 飞书用于数据输入/同步、人工阅读、审核、发布和异地备份，不作为经验检索逻辑的唯一底座。
3. **任何 AI 输出都必须能追溯。** 要保存它使用的数据快照、提示词版本、模型、证据来源和人工修改结果，不能使用 Codex 对话里的隐含上下文。

## 二、目标架构

```text
用户页面
  ├─ 周数据录入与校对
  ├─ 门店周报复盘
  ├─ 机会中心
  ├─ 验证与行动
  ├─ 经验库
  └─ 项目/门店档案
          │
          ▼
业务后端（真正控制流程）
  ├─ 事实服务
  ├─ 周报与复盘服务
  ├─ 机会服务
  ├─ 验证/实验服务
  ├─ 经验服务
  ├─ 文档发布服务
  ├─ AI 任务服务
  └─ 审计与版本服务
          │
   ┌──────┼───────────┐
   ▼      ▼           ▼
业务对象存储  AI 模型接口   飞书适配层
主事实与状态  分析候选结果   取数/落数/发布文档
```

### 1. 前端职责

前端只展示当前任务需要的信息和操作，不再自己承担正式数据存储。现有浏览器 `localStorage` 可保留为临时草稿和断网保护，但不能继续作为多人共用系统的主库。

页面建议调整为：

- **经营总览**：本周各门店状态、重点信号、待回答问题、正在验证的机会。
- **周数据**：录入、自动取数、来源说明、校验、飞书差异对比。
- **周报复盘**：按门店独立生成，完成因果调查、结论整理和正式周报。
- **机会中心**：跨周追踪机会，不让机会随周报结束而消失。
- **验证与行动**：记录假设、动作、指标、周期、结果和结论。
- **经验库**：搜索已经审核通过、具有适用边界的经验。
- **项目档案**：项目公共信息与门店差异信息分层管理。

### 2. 后端职责

后端需要从当前单文件接口逐步拆出清晰的业务模块，但第一阶段不要求拆成多个微服务。仍可保持一个部署进程，只需把职责模块化：

- `fact-service`：经营指标、经营事件、外部事件及来源。
- `profile-service`：项目公共档案、门店档案及历史版本。
- `review-service`：周复盘流程、信号、因果调查、周报版本。
- `opportunity-service`：机会的生成、证据、状态和跨周追踪。
- `experiment-service`：验证方案、执行记录、指标结果和复盘。
- `experience-service`：经验候选、审核、发布、失效和版本。
- `ai-task-service`：组装事实包、调用模型、校验结构、记录运行。
- `retrieval-service`：从档案、历史经验、历史机会和案例中检索相关材料。
- `feishu-adapter`：飞书取数、落数、比对、周报/经验发布。
- `audit-service`：记录谁在何时改了什么、AI 使用了什么。

### 3. 存储建议（按当前 EdgeOne 部署修订）

第一阶段不升级运行时、不注册外部数据库，也不要求使用者维护 SQLite 或 PostgreSQL。继续使用当前免费的 EdgeOne Makers 部署，并采用其内置的 **Blob 持久化存储**保存结构化 JSON 对象。

Blob 按目录组织数据，适合把项目、门店、周报、机会、验证、经验和 AI 运行拆成独立对象；正式状态读写使用强一致读取。业务层通过统一的 `repository/storage adapter` 访问数据，页面和业务流程不知道底层是 Blob。以后数据规模或并发真的超出 EdgeOne 能力时，只替换这一层即可迁移到关系数据库。

不采用“所有内容写进一个大 JSON 文件”的方式，而采用一对象一文件和独立索引，降低并发覆盖与单文件损坏风险。关键写入保留版本号、更新时间和追加式审计记录。

当前阶段无需 Node.js 22。只为现有 EdgeOne Functions 引入必要且兼容的依赖管理，不为了技术升级而改变可用的免费部署。

## 三、五类长期经营资产

### 1. 项目与门店档案

分为两层：

- 项目公共层：业务类型、产品形态、品牌定位、共同经营规则。
- 门店差异层：地址、场地、客群、商圈、渠道、产能、营业约束、成本和本地生态。

档案必须有版本和生效时间，避免后来修改档案后反向改变历史周报的解释背景。

所有门店采用同一套“门店模板”，但每家店保存自己的事实和配置。新增门店时只创建一份新门店实例，不允许在周报、经营地图、取数、提示词等模块中分别硬编码一个新店名。

数据路径始终带有稳定的 `project_id` 和 `venue_id`，例如：

```text
projects/{project_id}/profile
projects/{project_id}/venues/{venue_id}/profile
projects/{project_id}/venues/{venue_id}/weekly-records/{period_id}
projects/{project_id}/venues/{venue_id}/reports/{report_id}
projects/{project_id}/venues/{venue_id}/opportunities/{opportunity_id}
```

“同一个主库”只表示统一管理方式，并不表示把两家店的数据混在一起。跨店分析只有在明确选择多个 `venue_id` 时才会运行。

### 2. 经营事实库

包括：

- 周指标和日指标；
- 渠道、商品、次卡、核销、播控等结构化数据；
- 本周活动、排班、设备异常、场地事件、平台动作等经营事实；
- 天气、节假日、商圈活动等外部事实；
- 数据来源、采集时间、原始记录和人工修订。

事实与解释必须分开保存。运营说出的原因在确认前属于“待验证经营陈述”，不能直接变成正式因果事实。

### 3. 问题与机会台账

机会不能只存在于一份周报中。每个机会至少应保存：

- 发现了什么；
- 涉及哪个门店和指标；
- 证据和反证；
- 当前假设与置信度；
- 仍缺少什么信息；
- 当前状态；
- 是否已进入验证。

### 4. 行动与验证台账

“下一步动作”不能只是自然语言建议。进入正式执行前，需要具备：

- 要验证的假设；
- 具体动作；
- 负责人和时间；
- 成功/失败判断指标；
- 基线、目标和观察窗口；
- 可能干扰结果的因素；
- 实际结果与结论。

### 5. 经验库

经验不是普通总结，而是经过证据或验证支持的可复用判断。经验卡建议包含：

- 标题；
- 适用项目/门店/经营节点；
- 问题与背景；
- 关键机制或因果解释；
- 使用过的动作；
- 结果指标；
- 证据与来源周；
- 适用条件和不适用边界；
- 置信度；
- 审核状态和版本。

只有“验证完成且经人工确认”的内容才能成为正式经验。一般性的 AI 建议只能作为候选经验。

## 四、流程状态设计

状态由后端程序控制，AI 只能提供候选内容，不能自行推动状态。

### 周复盘

```text
草稿 → 事实就绪 → 信号就绪 → 因果调查中 → 可生成复盘
     → 人工筛选完成 → 正式周报 → 已发布
```

### 机会

```text
候选 → 待补证据 → 待决策 → 验证中
     → 已确认 / 已否定 / 持续观察 → 关闭
```

### 验证

```text
方案草稿 → 人工批准 → 待执行 → 执行中 → 已结束
         → 结果评估 → 转经验 / 不成立
```

### 经验

```text
候选经验 → 待审核 → 已发布 → 被新版本替代 / 已失效
```

## 五、AI 应该介入什么，不应该介入什么

### AI 适合完成

- 从结构化指标中判断哪些变化值得关注；
- 结合档案、经营事实和历史记录生成因果假设；
- 对运营回答进行相关性和证据充分性判断，并生成有限轮次的追问；
- 从历史经验和外部案例中解释相似性与差异；
- 生成机会候选和验证方案候选；
- 基于真实结果分析干扰因素，生成经验候选；
- 用已经确认的正式对象撰写周报。

### 程序必须完成

- 计算、汇总、环比、趋势和阈值判断；
- 日期、门店、渠道和字段映射；
- 数据来源追踪、飞书同步与差异比较；
- 组装每次 AI 调用的明确上下文；
- JSON 结构校验、必填项校验和数值一致性检查；
- 流程状态、权限、版本和正式落库；
- 控制追问次数和停止条件。

### 人必须决定

- 经营事实是否真实；
- 某个因果是否足够可信；
- 哪个机会值得投入；
- 哪个验证方案可以执行；
- 哪条结论可以成为正式经验；
- 哪些内容进入最终周报。

## 六、AI 调用架构

每次 AI 调用都应是一项独立、可复现的任务：

```text
任务类型
+ 门店/周期/经营节点
+ 当前事实快照
+ 项目与门店档案版本
+ 本次允许使用的历史经验/案例
+ 对话记录（仅限该卡片）
+ 提示词版本
+ 输出 JSON Schema
```

AI 返回后执行四层检查：

1. JSON 结构是否正确；
2. 引用的指标是否存在且数值一致；
3. 结论是否提供证据 ID；
4. 是否把假设冒充成事实。

每次运行保存 `fact_pack_snapshot`、模型、参数、提示词版本、原始输出、校验结果、人工修改和最终采用结果。这样未来更换 DeepSeek 或其他模型时，不需要改变业务流程。

## 七、飞书应承担什么角色

### 不建议

不建议新建一个类似 Word 的飞书文档，直接把它当作经验主库。原因是文档中的经验难以稳定拆分、筛选、关联门店、判断版本和被 AI 精确检索。

### 推荐做法

- **现有飞书表格**：继续承担经营事实的来源和正式落盘。
- **EdgeOne Blob**：承担机会、验证、经验、流程状态、AI 运行和版本的主存储。
- **飞书多维表格（可选）**：作为“已发布经验索引”，一行一条经验，方便团队查看、筛选和审核。
- **飞书文档（可选）**：发布最终周报、重要经验手册或专题复盘，不参与底层检索和状态控制。

如果建立飞书经验索引，建议字段为：经验 ID、标题、门店范围、经营节点、问题、背景、机制、动作、结果、置信度、适用边界、来源周期、证据链接、状态、版本、详情文档链接。

因此，当前不用急着创建飞书经验文档。应先把 EdgeOne Blob 中的经验工作流跑通，再决定是否同步一份给飞书供人阅读。

### 飞书异地备份

飞书云空间作为 EdgeOne 之外的灾备副本，不参与网页日常读写。备份包不包含模型 Key、飞书 App Secret 等秘密信息。

备份触发点：

- 正式发布门店周报后；
- 正式发布或更新经验后；
- 每次线上部署前；
- 每周至少生成一份完整备份。

备份目录建议：

```text
经营工作台备份/
  2026/
    08/
      backup_2026-08-31_周报发布后.zip
      backup_2026-08-31_部署前.zip
```

备份包包含项目/门店档案、周数据、周报、调查对话、机会、验证、经验、非敏感设置、对象版本和校验清单。恢复必须先校验包版本和完整性、展示影响范围并由人确认；恢复前再次保存当前快照，不允许静默覆盖。

首次实施可通过本机 `lark-cli` 创建目标文件夹、上传测试包并验证权限；正式运行后由 EdgeOne 调用飞书云空间接口自动上传。

## 八、可选 GitHub 组件

这些组件只解决技术问题，不替代本项目的经营逻辑。

| 组件 | 适合解决的问题 | 建议 |
|---|---|---|
| [XState](https://github.com/statelyai/xstate) | 周复盘、机会、验证等复杂状态和可测试的状态转换 | 可选但很适合。只用于执行我们定义的状态机，不让框架定义业务。 |
| [Ajv](https://github.com/ajv-validator/ajv) | 校验 AI 输出、事实包和接口 JSON Schema | 建议引入。项目已经有 Schema，Ajv 可替代分散的手写校验。 |
| [Promptfoo](https://github.com/promptfoo/promptfoo) | 用固定案例回归测试提示词、不同模型和 RAG 结果 | 建议作为开发测试工具，不进入用户流程。 |
| [Vercel AI SDK](https://github.com/vercel/ai) | 统一 DeepSeek、OpenAI 兼容接口和结构化输出 | 可选。最新版本需要更高 Node 版本；先完成 Node 22 迁移再评估，不是必要依赖。 |
| [EdgeOne Blob 示例](https://github.com/TencentEdgeOne/pages-blob-template) | 在现有 EdgeOne Functions 中持久化结构化 JSON 和文件 | 建议采用。与当前部署一致，不需要另建数据库账户。 |
| [Langfuse](https://github.com/langfuse/langfuse) | AI 调用链、提示词、耗时、成本和评估观测 | 后期可选。第一阶段先在本库记录 `ai_runs`，调用量上来再接。 |
| [Firecrawl](https://github.com/firecrawl/firecrawl) | 公网案例搜索、抓取和结构化 | 只作为后期可选数据源。自建依赖较重，第一阶段应采用人工指定网址或托管服务。 |

第一阶段不建议立即引入向量数据库。经验和案例数量较少时，使用结构化字段、标签、关键词和全文检索更可控；当有效经验/案例达到约数百条且召回明显不足时，再增加向量检索。

## 九、实施顺序

### 阶段 0：保护现状与建立底座

- 导出并备份浏览器草稿、现有报告、服务器 JSON 和飞书关键区域；
- 保持当前 EdgeOne 运行环境，建立必要的依赖清单和锁文件；
- 建立 EdgeOne Blob 数据空间、数据迁移脚本、追加式审计记录和统一 ID；
- 把当前 `localStorage` 主数据迁入后端，保留一版只读回退；
- 建立提示词版本、AI 运行记录和事实包快照。

验收：换浏览器或换电脑后仍能看到相同记录；历史数据不丢；AI 运行可复现。

### 阶段 1：重建周复盘流程

- 按门店生成独立事实包和独立周报；
- 项目公共档案与门店档案分层；
- 信号、因果问答、复盘结论成为明确对象；
- 限制追问轮次并记录停止原因；
- 最终周报只读取已确认内容。

验收：两家门店互不串数；重新生成不会无故覆盖人工确认；每个结论能追溯到事实。

### 阶段 2：建立机会中心

- 将周报中的问题和机会转为跨周台账；
- 支持证据、反证、状态、负责人和观察周期；
- 关联历史同类信号、经营事实和已发布经验；
- 区分“问题”“机会”“待观察信号”。

验收：机会不会随着某周结束消失；同一机会不会每周重复创建。

### 阶段 3：建立验证与经验闭环

- 建立验证方案、执行和测量结果；
- 自动计算前后变化，AI 只解释机制和干扰因素；
- 验证结论生成一个或多个经验候选；
- 人工审核后发布到经验库。

验收：每条正式经验都有来源、证据、适用边界和版本。

### 阶段 4：文档和管理输出

- 生成门店周报；
- 生成跨门店管理摘要；
- 一键发布/复制到飞书；
- 可选同步已发布经验到飞书多维表格或经验手册。

验收：正式周报是闭环结果的可读表达，不再夹带待回答问题和未确认假设。

### 阶段 5：模型质量与运行观测

- 用真实历史周建立 Promptfoo 回归集；
- 比较模型、提示词版本和成本；
- 对错误引用、空洞建议、重复问题、无证据机会建立自动断言；
- 调用量上升后再评估 Langfuse。

## 十、迁移原则

- 现有飞书经营事实不做破坏性重写；
- 旧版合并周报作为 `legacy` 历史保留，新周报开始按门店生成；
- 现有档案 JSON、知识 JSON 导入 EdgeOne Blob 并标记来源和版本；
- 来自硬编码或旧对话、无法验证的内容标记为 `legacy_unverified`，不得直接当作正式事实；
- 浏览器数据迁移成功后，至少保留一个版本的只读兼容和可回滚备份；
- 每个阶段单独上线和验收，不采用一次性大爆炸替换。

## 十一、需要你准备或确认的内容

### 开始阶段必须确认

以下项目已根据本次确认收敛，不再要求使用者理解服务器或数据库运维：

1. **运行环境**：保持当前 EdgeOne，不升级 Node.js。
2. **存储选择**：使用 EdgeOne 内置 Blob，不注册 SQLite/PostgreSQL 服务。
3. **主库原则**：Blob 中的结构化业务对象是机会、验证、经验和流程状态的权威来源；飞书继续是事实来源/落盘和发布层。
4. **角色模型**：先定义“运营填报、经营审核、系统管理”三种权限，不要求现在提供具体姓名；单人使用时同一账号可以拥有全部权限。
5. **门店模型**：首批门店为东坝店和中影店。系统为其生成稳定机器 ID；以后新增门店通过统一门店模板创建，不修改各模块代码。
6. **备份方式**：EdgeOne 内保留版本和快照，飞书云空间保存平台外备份；系统提供一键导出和受控恢复，不要求使用者选择服务器目录或执行数据库命令。

### 第一至三阶段需要逐步补充

- 每家店的产能、营业时间、人员、主要产品、价格、成本/毛利、不可改变的约束；
- 6—8 周相对完整的历史数据；
- 已知的经营活动、异常和结果，哪怕只有 3—5 个真实案例；
- 经验由谁审核发布；
- 哪些经营指标可以作为验证成功标准；
- 外部案例检索允许使用什么服务、预算和频率。

### 可以以后决定

- 是否建立飞书多维表格经验索引；
- 最终周报发布到哪个飞书文件夹或知识库；
- 是否接入 Langfuse、Firecrawl 或向量数据库；
- 当数据量和并发明显超出 EdgeOne Blob 适用范围时，是否迁移到关系数据库。

## 十二、推荐落地选择

如果以当前规模、风险和实施成本综合判断，推荐采用：

- 保持当前 EdgeOne Makers 免费部署和现有运行环境；
- 单体模块化后端，不上微服务；
- EdgeOne Blob 保存结构化业务对象，并提供版本、自动快照和一键导出；
- Ajv 做事实包和 AI 输出校验；
- 自有 AI 适配层继续兼容 DeepSeek，不急于引入 AI SDK；
- 显式状态表起步，流程复杂度继续增加时引入 XState；
- Promptfoo 作为提示词与模型回归测试；
- 飞书继续做事实表和发布层；
- 经验正式主库放在 EdgeOne Blob，飞书经验库仅做可选阅读镜像；飞书云空间同时保存加密凭证以外的完整灾备包。

这一路径既能解决当前本地存储、流程平铺、经验无落点和 AI 上下文不透明的问题，也不会为了引入一套“大框架”而重写全部项目。
